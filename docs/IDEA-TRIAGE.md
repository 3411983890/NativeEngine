## 3. 四条"现在就做"的具体切片

### 3.1 A：确定性契约 + 黑匣子（最高优先）

**现状（已核实）**：`engine/native/game.cpp`（375 行）已有 120 Hz 固定步长与累加器、场景 revision、`--smoke` 无头模式；**当前原生代码里没有任何随机源**（grep 无 `rand`/`mt19937`/`random`），这对建立确定性契约是利好——现在只需"注册机制 + 禁止私接"，不必先做迁移。
**第一步**（S）：
1. 在 `Game` 里加 `WorldHash`：对位置/朝向/门/钥匙/门状态做定点量化后 FNV-1a，每 tick 输出一个 u64。
2. 建立 RNG 流注册表（gameplay / VFX / AI 各一条，种子随场景 revision 派生），禁止私有 `rand()`；现在还没有随机源，此时立规矩成本最低。
3. 加 `--record <file>` / `--replay <file>`：只记录输入帧 + 场景 revision + 哈希序列。
**验收**：
- 同场景两次独立运行 1000 tick，哈希序列逐位相同（`reports/latest/determinism.json`）；
- 录制 30 s 回放重放 diff=0；
- 注入一次 GPU 卡顿（sleep）不改变 gameplay 哈希（证明渲染不影响判定）。

**为什么这是"创新"而不是"补作业"**：绝大多数引擎把确定性当"网络模块的副产物"；把它提升为**带哈希断言的一等契约**后，回放/时间旅行/崩溃复现/世界分叉全部变成"免费能力"，而这些正是我们做 Nanite/Lumen 时最需要的调试基础设施（时域非确定会让截图证据失效）。

### 3.2 B：误差契约 + 引擎内参考实现

**现状**：Nanite/Lumen 方案里已有"path-traced ground truth"；场景构建已有内容哈希（`BUILD_CONFLICT` 篡改检测）。
**第一步**（M）：
1. 定义 `ApproximationContract { name, reference, metric, budget, sampleScene }`，登记在 `docs/CONTRACTS.md` 并由脚本校验。
2. 第一批三个契约：① Nanite LOD 误差（vis buffer vs 全分辨率参考）；② Lumen `lite/swrt/hwrt` 相对 path-traced 参考的 relMSE；③ 阴影 pass 相对"逐像素全量追踪"的差异。
3. 参考图/指标随证据一起归档（复用现有 `reports/<version>/<commit>/`）。
**验收**：三个契约在 CI 里各有阈值与失败日志；改一行渲染代码若越界必须红。

**额外创新（清单里没有，但很便宜）**：把"生成物可返参"的**溯源**部分先落地——场景包 manifest 增加 `generator`（工具名+版本+种子+参数），任何资产/场景都能回答"谁生成的、能不能重生成"。这与 `BUILD_CONFLICT` 同源，成本极低。

### 3.3 C：预算管理器（把"资源经济学"做成服务）

**现状**：已有分段时间戳（整帧 / DispatchRays）、P50/P95、版本化证据。
**第一步**（M）：
1. `FrameBudget` 服务：各子系统（光栅/DXR/Mesh/合成/未来 Nanite/Lumen）**申领**预算，帧末对账。
2. 两级策略：软超预算 → 降低可降档项（GI ray 数、cluster 误差、阴影分辨率）；硬超预算 → 降档（lumen-lite / 关阴影）并记事件。
3. 每插件声明**性能契约**（"本功能在目标硬件 1280×720 下 GPU ≤ 1.5 ms"），CI 在目标硬档（现在是 RTX 5060）上跑，超了红。
**验收**：`reports/latest/budget.json` 含每子系统申领/实耗/降档事件；人为把预算调低必须触发降档而不是掉帧；Nanite/Lumen 接入后同一份报告自动包含它们。

### 3.4 D：设计期 lint + 世界查询（Spec → Verify 的薄切片）

**现状（已核实）**：`assets/scene.schema.json`、JS 校验器、事务与撤销已就绪；`queryScene` 目前只支持 `kind` / `entityId` / `name` 三个**结构化**过滤字段，**没有空间谓词**；`tools/scene.mjs` 可被 MCP 调用。
**第一步**（S–M）：
1. `tools/lint.mjs`：可达性（从小院出生点能否走到终点）、钥匙/门依赖、掩体规则、性能预算（实体数/材质数上限）。
2. 空间谓词查询：`within(entity, radius)`、`visible(from, to)`、`reachable(x, y)`，复用 lint 的导航图。
3. 把 lint 接进 `verify.ps1` 与 MCP（`scene_lint` 工具），失败给出**可读的因果链**（哪条规则、哪个实体、为什么）。
**验收**：故意把钥匙放到不可达位置 → lint 报错并指出实体 ID；CI 门禁失败信息可直接贴进 issue。

**为什么值得现在做**：这是清单里 #8/#9/#10 的公共地基，也是"AI 代理能用"的前提——代理需要能**查询世界**、能**被规则挡住**，而不是只能读文件。

## 4. 我建议补充的创新（清单里没有，但与它互补）

1. **Replay-as-evidence**：bug report = 一个 `.replay` + 哈希链 + 当时的预算快照；`reports/` 里可直接回放。把"文字描述 bug"变成"可执行复现"。
2. **契约注册表（Contract Registry）**：确定性、误差、性能三种契约用同一份清单登记、同一套 CI 执行、同一套报告呈现。避免三套门禁各写各的。
3. **世界分叉做 CI**：`--fork N` 并行跑 N 个确定性 headless 实例，同一输入不同策略 → bot 覆盖率/平衡性扫参。成本低（现有 smoke 架构 + 确定性内核）。
4. **语义 diff 的影响分析**（#14 的薄切片）：改一个材质/实体 → 用场景图算出"影响哪些关卡、预算变化多少、哪些 lint 规则会红"。不需要 CRDT 也能先给设计者价值。
5. **场抽象的第一消费者**：导航/可达性用稀疏占据场实现，存储直接放进 Nanite 几何包（同一份体素供 Lumen 远场 SDF 复用）。**先证明"一个场两个消费者"，再谈六个。**
6. **"能力-契约-证据"发布门**：把 G1 的模式产品化——每个工作包都必须提交能力矩阵、契约对账、证据目录三件套，才能打 tag。

## 6. 风险与反模式

- **清单化陷阱**：22 条一次上 = 项目猝死。本文的价值就是"只做 4 条，其余挂起"，并且每条都要有验收。
- **Goodhart 效应**：指标一旦成为门禁就会被优化到失真（例如为了 relMSE 降低而牺牲观感）。对策：多指标 + 固定机位人工抽检 + 参考图版本化。
- **确定性开销**：每 tick 哈希、因果元数据都有成本；对策：哈希可分区（只哈希 gameplay 子集）、因果追踪只在诊断模式全开。
- **契约维护成本**：契约太多会变成官僚；对策：每条契约必须有"参考实现 + 采样场景 + 阈值来源"三要素，否则不登记。
- **与本项目现有约定的冲突**：不改变 G1、不改变"先确认再开工"、不改变"能力≠效果"的字段约定。
