NativeGPU 的分层不是按"模块大小"切的，而是按谁能改什么切的。内容、工具、AI、编辑器、运行时、渲染器六层之间只有窄接口，且所有写操作都必须穿过同一道事务闸门。

已冻结 RHI 边界见 .developmentAgent/rendering/RHI.md · 几何架构见 .developmentAgent/rendering/GEOMETRY-LAYOUT.md

六层结构

┌──────────────────────────────────────────────────────────────┐
│ ① 内容层   assets/                                          │
│    .scene.json · .ngtex · scripts/*.lua · animation/*.bin    │
├──────────────────────────────────────────────────────────────┤

│    validate · preview · commit · undo · recover · query · lint│
├──────────────────────────────────────────────────────────────┤
│ ③ AI 层    ai/                             （stdio MCP）     │
│    12 个工具，只能调用 ② 与受控进程启动                       │
├──────────────────────────────────────────────────────────────┤
│ ④ 编辑器   editor/                     （Electron / Web）    │
│    草稿 → 差异预览 → 提交；原生进程管理；按需快照              │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 运行时   host/ + engine/native/            （C++17）       │
│    输入 · 120 Hz 固定步长 · 物理 · 动画 · 玩法 · 摘要         │
├──────────────────────────────────────────────────────────────┤
│ ⑥ 渲染     renderer/ + shaders/              （D3D12）       │
│    RHI::Device → 光栅 / DXR / Mesh / compute · 证据上报       │
└──────────────────────────────────────────────────────────────┘

关键约束：② 是唯一的写入路径。③ 和 ④ 都不持有直接写 assets/ 的能力，它们调用的是同一份 engine/scene/ 实现。这条约束让"编辑器改的"和"Agent 改的"在语义上完全等价，也让审计只需要看一个地方。

帧路径

宿主每帧只做四件事：收集输入、推进固定步长模拟、构造绘制列表、提交给 RHI。渲染器不认识"实体"，只认识 DrawItem 与 LightDesc。

host/main.cpp
   │  输入采样
   ├─▶ Game::update(input, dt)          // 累加器 → N × 1/120 s
   │      物理 · 动画 · 玩法 · 摘要
   ├─▶ Game::drawItems()  → std::vector<DrawItem>
   └─▶ nativegpu::rhi::Device::submit(viewProjection, eye, draws, lights)
            │
            └─▶ nativegpu::Renderer (D3D12)
                  深度 pass · 双目标光栅 · DXR 阴影 · 合成 · 体积 · UI

Device 是 R06 冻结的最小边界，只有 9 组方法：生命周期、resize、submit、质量开关、截图、证据查询。它不是完整 RHI——没有资源/管线对象、没有多队列、没有绑定模型。故障注入、对象计数这类测试钩子被明确排除在边界外，通过 nativeHandle() 取回后端指针使用。

固定步长与渲染解耦

模拟固定 120 Hz，渲染不推进模拟。60 FPS 时每帧两个 tick；240 帧冒烟 = 480 tick，这是确定性证据里被断言的事实。帧间隔只由宿主传入，模拟代码不允许读墙上时钟——这条规则由静态扫描强制执行。

数据流：一次改动经过什么

Agent / 编辑器
   │  { projectId, expectedRevision, commands[] }
   ▼
engine/scene/index.mjs
   ├─ 应用到副本 → 全量校验 → 失败则整批拒绝
   ├─ 写 .pending.json → 原子替换 .scene.json → 写 .history.json
   └─ revision + 1
   ▼
NativeGPU.exe（每 ~400 ms 轮询）
   └─ 加载新 revision → 重建玩法与渲染资源 → 报告 hotReloads +1

失败不会留下半个场景：要么旧 revision 继续服务，要么整批拒绝并返回结构化错误。.snapshot.json 保存上一有效场景，.pending.json 用于中断恢复，.lock 阻止同一文件并行写入。

证据如何产生

每次 verify.ps1 / ci.ps1 都在 reports/<version>/<commit12>/<UTC 时间戳>/ 下新建目录，并刷新 reports/latest/ 别名。同一输入重跑不会覆盖历史证据。

run.json 记录：commit、worktreeDirty、staleBuild、Node 版本、适配器名称与驱动、DXC 版本、场景哈希，以及每个产物的 SHA-256。这份文件是"这次数字可信吗"的唯一依据。

当前架构的边界

只有一个图形后端（d3d12），supports("vulkan") 为 false；Device 不是完整 RHI；没有运行时 glTF 导入；没有内嵌实时视口（编辑器用的是独立进程 + 按需快照）。这些不是"以后补一下"，而是明确排在路线图上的工作包。
