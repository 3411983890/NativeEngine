错误码是契约，错误文本不是。调用方只应该对 code 做分支，message 随时可能为了可读性改动。

稳定 来源：各模块 throw 点 · .developmentAgent/core/STATUS.md §维护约束

错误信封

{
  "ok": false,
  "error": {
    "code": "NG-E-MAT-STALE",
    "message": "material handle generation mismatch",
    "details": []
  }
}

无法归类的异常统一包成 TOOL_FAILURE——它的出现说明有未被分类的失败路径，应当被修掉，而不是被依赖。

场景层错误码

场景事务使用裸大写码（不带前缀），这是历史原因，也是公开契约的一部分。

码含义能否重试
PROJECT_MISMATCH事务的 projectId 与场景不符否，改 ID
REVISION_CONFLICTexpectedRevision 过期是，重新读取后重试
INVALID_SCENESchema / 不变量失败否，修数据
INVALID_COMMAND未知 op 或命令结构错误否
INVALID_JSONJSON 解析失败否
DUPLICATE_ENTITYUUID 重复否
ENTITY_NOT_FOUND目标实体不存在是，重新查询

处理建议

  1. 只对 code 分支。 不要用 message.includes(...) 判断错误类型。
  2. 区分可重试与不可重试。 上表的"能否重试"列就是依据；REVISION_CONFLICT 是正常的并发结果，不是 bug。
  3. 失败要留证据。 报告里的 error 字段与 dispatchFailures 这类计数，比控制台日志更可靠。
  4. 不要吞掉 TOOL_FAILURE。 它意味着有一条失败路径没被分类，应该补一个错误码。
