让 AI 做地图，难点从来不是"让它吐 JSON"——那今天就能做到。难点是：它吐出来的东西必须可复现、可局部修复、可被机器判定为"能用"。这一页给出完整路径，以及一条硬结论：AI 该产出的是 500 token 的规格，不是 36,000 token 的场景。

设计稿 验证链路已存在 目标版本 0.12+ · 依赖地形系统（未实现）
这条路径的地基已经在了

事务层、12 条 lint（含步行可达性）、9 种实体、植被散布、固定机位截图、图像回归、帧预算、确定性回放——这些不是要新建的东西，而是已经有了、只是还没串成一条生成回路。所以这一页的重点不是"造轮子"，是"定契约"。

一、起点：你们已经在做 AI 地编了

先看一个容易被忽略的事实：assets/town.scene.json 不是手写的，它由 tools/town/gen-scene.mjs 生成。而那个生成器里，整个城镇的布局是一张 10 行的常量表加一个循环：

const buildings = [
  { side: -1, z: -26, width: 9, height: 7.0,  wall: 'brick_red',  floors: 2, awning: true },
  { side: -1, z: -16, width: 9, height: 8.6,  wall: 'plaster',    floors: 3, awning: false },
  { side: -1, z:  -6, width: 9, height: 12.0, wall: 'brick_grey', floors: 4, tower: true },
  // ... 共 10 个地块
];

这就是一张人类手写的 MapSpec。所以"AI 地编"要替换的对象不是场景 JSON，而是这张表——把常量换成模型产出的规格，把循环换成求解器。架构上不需要新范式，只需要补上中间那层。

为什么不能让模型直接写场景

事实数值含义
town 场景体积237 KB / 608 实体 / 120×132 m这是当前"一张完整地图"的实际量级
单实体 JSON平均 205 B ≈ 57 tokenUUID + 名称 + 位置 + 尺寸 + 材质 + 碰撞
整场景输出≈ 36,000 token一次生成就吃掉整个输出预算，且无法 diff
实体密度0.038 /m²可直接换算任何地图规模的预算
10,000 实体上限≈ 0.26 km²密度不变时的理论上限
120 m 视距下的一张图150×150 m ≈ 860 实体舒适区：留 10 倍余量给细节与植被

把 36,000 token 的输出拿去做迭代是行不通的：改一个街区要重出全文，改错了无法回滚到"第 400 个实体之前"，两个版本的差异没法看，模型也无法理解自己上一版错在哪。而一张 2 KB 的规格表 ≈ 500 token，迭代成本降低 60 倍，还能进 Git 做 diff。

一条纪律

场景 JSON 是构建产物，不是源文件。任何把 .scene.json 当手写源文件、让模型整篇覆盖的做法，都会在第二次修改时崩掉——因为它同时丢掉了种子、意图和可回滚性。

二、"完整可用"是五条可执行合同

"可用"如果只是形容词，AI 就永远无法被追责。所以先把验收写成断言——每一条都对应仓库里已经存在的命令。

G2可玩12 条 lint 零 error：无重叠、无越界、门有钥匙node tools/scene.mjs lint --json硬门禁

四、MapSpec：模型唯一该写的东西

规格的设计目标有三个：字段少到模型不会写错、语义强到求解器不用猜、体积小到可以反复迭代。

{
  "schema": "nativegpu.map/1",
  "seed": "harbour-0714",
  "theme": { "culture": "north-european", "era": "industrial", "palette": "cold-damp" },

  "terrain": {
    "extent": [160, 160],
    "relief": "coastal-hills",        // 求解器内置的地形原型，不是自由文本
    "reliefStrength": 0.55,           // 0..1，映射到 ±25 m
    "water": { "kind": "bay", "level": -2.0, "edge": "south" },
    "erosion": { "hydraulic": 0.6, "thermal": 0.3, "iterations": 240 }
  },

  "settlement": {
    "kind": "harbour-town",
    "footprint": [110, 90],
    "density": 0.62,                  // 建筑覆盖率
    "grid": 4.0,                      // 结构模数，必须是 1 m 的倍数
    "storeys": [2, 4],
    "landmark": { "count": 1, "role": "church-tower", "at": "street-end" }
  },

  "gameplay": {
    "objective": "fetch-and-return",
    "route": { "length": [120, 180], "loops": 1 },
    "challenge": { "gates": 1, "verticality": "low" }
  },

  "presentation": {
    "timeOfDay": "dusk", "weather": "mist",
    "heroShot": { "subject": "landmark", "framing": "three-quarter" }
  },

  "budget": { "entities": 900, "drawCalls": 1200, "targetMs": 16.6 }
}

三条纪律，缺一条就会退化成"模型在猜坐标"：

不写坐标
没有 position、没有 scale。位置是求解结果，不是输入。
不写实体
没有 entities 数组。数量由密度与地块决定，不由模型数出来。
必带 seed
同一份 spec 在任何机器、任何时间都必须产出同一张地图。seed 是规格的一部分，不是运行时参数。

relief、kind 这些字段是枚举而不是自由文本，这是刻意的：让模型在有限词汇里做选择，比让它描述"一个有点像挪威渔村但更破败的地方"可靠得多。自由文本只能出现在 theme.palette 这类纯表现字段上，且必须映射到已存在的材质名。

五、求解器：把"像"变成"算"

5.1 地形：一个顶层块，不是一种实体

地形不该做成第 10 种 kind。理由是三个具体约束：它不该占用 10,000 实体预算；它不该进 TLAS（否则 66k 顶点要逐块进加速结构）；一张图通常只有一块地形，而 kind 的语义是"可增删的实例"。

所以它应该和 lighting、materials 并列，作为文档级资产引用：

"terrain": {
  "file": "terrain/harbour.r16",
  "sha256": "…",
  "size": [257, 257],          // 顶点数，257² = 66,049
  "extent": [160, 160],        // 米
  "heightRange": [-25, 25],
  "splat": "terrain/harbour.splat"
}
项数值说明
高度图源257² × 2 B = 132 KBR16，0.62 m 精度，25 cm 高程分辨率
顶点缓冲66,049 × 32 B = 2.1 MBpos3 + normal3 + uv2
索引缓冲393,216 × 4 B = 1.6 MB256² 格 × 2 三角
绘制1 次一次 DrawIndexedInstanced，无需 LOD（far = 120 m）
权重图257² × 4 B = 264 KBRGBA8 装 4 层：草 / 岩 / 沙 / 路

碰撞上有一条明确的不做：不做 heightfield 刚体。物理是 120 Hz 盒体 SAT + 凸包窄相，heightfield 是另一个量级的工作，而且角色根本不需要它——角色只需要一个贴地查询。

// CPU 侧双线性采样 + 中心差分求法线；O(1)，无状态
float3 sampleTerrain(float2 xz);   // 返回 (y, nx, nz)
bool   walkableAt(float2 xz);      // 坡度 < 阈值 && 不在水面下

真正让地形"接得进去"的是一个已经存在的接缝。植被系统里的 SurfaceSampler 从一开始就把"地面是什么"抽象成了接口，注释写得很直白：

// engine/vegetation/surface.mjs
// A static triangle soup sampled vertically. This is the adapter for an already
// imported scene mesh; a terrain height field is a different adapter with the same
// interface, which is why the sampler owns the query instead of the scatter code.

也就是说，地形接入植被不需要改散布代码，只需要加一个 HeightfieldSurface，实现同样的 heightAt / normalAt / materialAt 三件套，并把 sampler 版本号写进 cook 记录——地形一改，旧散布自动失效，而不是悄悄浮空。

5.2 骨架：路网 → 地块 → 高度场

因为实体没有旋转（components.transform.yaw 在 schema 里存在，但原生渲染与物理都不消费它），所有几何都是轴对齐盒体。这不是缺陷，而是风格约束：它把设计空间压成了网格语法，而这正是生成式系统最容易做对的形式。

  1. 路网：在 4 m 粗网格上跑最小代价路径，代价 = 坡度² + 水面惩罚 + 已有道路折扣。结果是正交或 45° 折线（折线用短盒段拼接，因为不能旋转）。
  2. 地块：沿街做 BSP 递归切分，每块必须有一段临街面（frontage ≥ 4 m），进深 8–14 m。切分树本身是确定性的，seed 只影响切分位置。
  3. 高度场：每个地块的高程取四角地形高度的中位数，地块内部填平——这样建筑不会歪在坡上，而街道保留起伏。这一步是"看起来像人做的"和"看起来像程序堆的"的分界线。

5.3 结构：立面是一张模块表

一栋建筑 = 沿街立面按 1 m 模数排布的模块序列：wall / window / door / shopfront / awning / sign，每层一行，屋顶用坡顶或平顶收口。模块本身就是盒体 + 材质槽，所以这条路完全落在现有表达力内，不需要任意网格。

生成时只需要决定三件事：层数（由密度场给出）、开间节奏（seed 驱动的交替模式）、材质套系（由 theme.palette 映射到已有的 brick_red / plaster / stone 等名字）。其余全是查表。

5.4 细节：复用已有的散布系统

道具与植被都走同一条路：规则 + 种子 → 内容寻址包，不进场景实体。植被系统的 scatter.mjs 已经实现了"坡度 / 高度 / 到路距离 / 簇噪声"四类规则，草的密度按距离降级。AI 在这里要做的只是从 spec 推导规则参数，而不是重新发明散布算法。

这条分工很重要

散布是性能问题（页、量化、LOD、impostor），不是生成问题。把 10,000 棵树塞进场景 JSON 会同时撞上实体上限和事务层。让 AI 碰散布参数、不碰散布实现。

5.5 玩法：把 lint 的洪泛反用成求解器

这是整条路径里最省力的一步。lint 已经有一个 0.5 m 栅格的步行可达性判定（KEY-UNREACHABLE / GOAL-UNREACHABLE），它本质上是在算连通分量。生成时用同一个算法做构造，而不是事后判定：

  1. 先铺满可行走地面，跑一次洪泛 → 得到若干连通分量。
  2. 取最大的两个分量，找出它们的邻接边（只隔一堵墙的地方）。
  3. 门就放在那条边上，钥匙放在 A 侧，终点放在 B 侧。
  4. 出生点选在 A 侧、离门最远且视野开阔的位置。

这样出来的地图构造上就满足 G3，不靠重试。判定与生成共用一个图，是最划算的复用——否则你会陷入"生成 → lint 报不可达 → 改一处 → 另一处又断了"的循环，而每次循环都要花掉一次模型调用。

六、修复闭环：只有规格级失败才回模型

门禁失败时，第一反应不该是"让模型重写一遍"。绝大多数失败是几何级的，求解器自己能修，而且修得比模型准。

失败类型典型 code修复算子回模型？
几何重叠NG-LINT-OVERLAP沿最小穿透轴推开，或删除低优先级道具否
越界 / 埋地NG-LINT-OUT-OF-WORLDclamp 到 worldExtent，抬高到地面以上否
终点不可达NG-LINT-GOAL-UNREACHABLE在最近阻挡体上开 1.2 m 缺口否
钥匙在门后NG-LINT-KEY-AFTER-DOOR交换两侧归属，重跑 5.5 的分配否
实体超预算NG-LINT-ENTITY-BUDGET降低散布密度 / 合并同材质薄片规格级：是
帧时间超标budget.status = exhausted降阴影档 / 降植被密度规格级：是
画面退化G5 覆盖率过低枚举可行机位，重选 hero shot否
schema 违规NG-E-SCENE-SCHEMA不修——这是 emitter 的 bug否，抛给工程

最后一行是关键：schema 违规说明代码写错了，不是模型想错了。如果把它当成"模型输出不合格"去重试，你会得到十次相同的失败，并且永远修不好那个 emitter。

所有修复都走事务：preview → apply，留下 diff 和 expectedRevision。这样"AI 改了哪几刀"是可审计的，而且任何一刀都能 undo。这一条直接复用现有的事务层，不需要新机制。

七、观感不是玄学，是四条可计算的构图约束

盒体 + 平面投影 UV 的表达上限确实存在，但它不等于"一定难看"。难看的典型原因是构图而不是材质。有四条规则可以用几何查询近似判定，成本很低：

视线终点要有地标
沿主街方向投射射线，终点 40 m 内必须有高于两侧 1.5 倍的体量。否则街道会"泄气"。
街道高宽比 1 : 1 ~ 1 : 1.5
由地块进深与层高直接算出，生成时就能约束，不需要事后调。
主光与相机夹角 30°–60°
从 lighting.keyDirection 与 hero 机位方向点积得出。夹角太小没有体积感，太大全是阴影。
雾要把远景压成三层
用 fogDensity 反算可见深度，确保前景/中景/远景各有一层，而不是一片灰。

这四条都不需要"审美模型"，只需要射线与视锥查询。真正需要人的只有一件事：接受基线。

九、明确不做

边界
  • 不做"一句话出 3A 地图"。表达面是盒体 + 9 种 kind + 平面投影 UV，上限是"风格化的正交聚落"，不是写实。
  • 不让模型输出坐标或实体。破坏这条，可复现与局部修复同时失效。
  • 不做 heightfield 刚体。只做贴地查询；物理仍是盒体与凸包。
  • 不做旋转几何。yaw 字段今天不被渲染与物理消费，先补 OBB 路径再谈斜街。
  • 不用自动指标替代审美。G8 由人接受；机器只判"是不是坏图"。
  • 不做扩散模型直出高度图并直接使用。必须过侵蚀仿真（水力 + 热力 + 流量累积），否则流域不连续，一眼假。

下一步

如果只做一件事，做 P0：把 tools/town/gen-scene.mjs 里那 10 行常量表换成一份 map.json，再加一个 60 行的发射器。它不会让画面变好，但会立刻暴露规格设计里的所有问题——而这些问题是后面五个阶段都要踩的。
