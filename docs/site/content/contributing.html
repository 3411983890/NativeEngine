这个仓库对"完成"的定义比多数项目严格：能跑不算完成，要能回退、有报告、能重放。贡献指南就是把这条标准写成人能执行的清单。

文档规范

每篇设计文档的开头必须有四行元信息，缺一行就会被评审打回：

- 版本：v0.1（设计稿 / 已实现 / 部分实现）
- 日期：YYYY-MM-DD
- 基线：NativeGPU x.y.z（当时的真实版本）
- 状态：待评审 / 进行中 / 已冻结
规则原因
设计稿必须写"未实现，不是能力声明"防止方案文档被当成功能清单引用
每个系统必须有"明确未实现"清单含糊其辞比承认缺失更贵
数字必须标注来源报告与机器跨机引用会制造假基线
不写"大概""应该""基本完成"这些词无法被验证
改契约要同步四处见下节

契约同步：四处法则

任何场景字段的增删改，必须同时改四个地方，缺一不可：

  1. assets/scene.schema.json——机器可读的唯一真相
  2. engine/scene/index.mjs——Node 校验器
  3. host/scene_loader.cpp——原生加载器
  4. docs/ 下对应文档 + 本份站点内容

只改三处，第四个地方就会成为"文档说支持、代码不认"的分裂点。评审时第一个看的就是这四处是否一致。

证据纪律

禁止正确做法
手写 implemented: true由运行报告写出，代码只读
手写性能数字跑脚本，引用 reports/ 里的产物
为了通过测试删除测试修实现，或显式记录放宽原因
放宽 schema 让脏数据通过改数据，或走版本迁移
用空场景/静默重置掩盖热重载失败保留上一有效场景并报错

高级图形能力只有在可运行 + 可回退 + 有报告三条都满足后，才能把 implemented 改成 true。

新增一个系统

1. 写设计文档（含边界与验收标准）
2. 定数据契约（schema / 结构体 / 文件格式）
3. 实现最小可运行切片 + 回退开关
4. 写证据脚本（断言 + 固定机位截图 + 报告字段）
5. 接入 verify.ps1 / ci.ps1
6. 更新 README 能力表 + .developmentAgent/core/STATUS.md + 本站文档

第 3 步的"回退开关"不是可选项：没有回退，就无法证明"关掉它时行为和以前一致"，也就无法定位回归。

扩展玩法能力

  1. 登记组件字段及版本
  2. 注册原生系统，或添加 Lua 行为
  3. 通过命令 / 事件交互，不直接改别人的状态
  4. 补恢复、确定性与字段校验测试

原生系统用 Runtime::registerSystem 声明名称、Phase、after 和接收 Runtime& 的回调。回调不得捕获临时 World 指针；持久数据必须进组件，不能藏在外部全局变量里。

评审清单

  • 新增字段是否四处同步？
  • 新增开关关闭时，是否与改动前逐像素/逐字节一致？
  • 是否引入了未命名的随机或墙上时钟？
  • 失败路径是否返回稳定错误码，而不是抛裸异常？
  • 报告字段是否区分"能力可用"与"效果生效"？
  • 文档的"未实现"清单是否更新？
  • 是否能在干净树上用 ci.ps1 -Clean 重放？

维护本份站点

本站点是生成的，不要直接改 dist/：

docs/site/nav.json            侧边栏结构
docs/site/content/*.html      每页正文片段（不含 shell）
docs/site/assets/             样式与脚本
docs/site/build.mjs           生成器

npm run docs                  # 重新生成 docs/site/dist/

新增页面只需两步：在 nav.json 里加一项，在 content/ 下建同名 .html。目录、上一页/下一页、搜索索引会自动更新。

为什么用生成器而不是手写多页

多页 HTML 在 file:// 下能直接打开，不依赖本地服务器；但侧边栏、目录、搜索索引在每页重复。生成器把"重复"收敛到一处，同时保留多页的离线可用性。
