# 真实水体持续目标开发记录

目标依据：[系统方案](WATER-REALISM-SYSTEM-PLAN.md)。2026-10-27 用户明确要求以开发真实水体为 goal。目标仍在进行，不能以任何单次水塘演示或事件计数宣告完成。

### 波纹形状与逐次变化（2026-10-27 深夜）

用户反馈两点：交互后的波纹**方形扩散**、**每一个波纹都一样**。两点都成立，各有独立原因。

- **方形来自网格分辨率，不是配色。** 离屏探针（一次交互后 36 tick 的高度图）显示 0.125 m 网格（64×64）的环带是**方形带圆角**——波前的色散误差在方形网格上沿轴向快、对角线慢；换到 0.0625 m（128×128）后同一条环变圆。项目水体资产因此加密：`cellMetres 0.125 → 0.0625`、`budget.maxCells 4096 → 16384`，重新 cook 后场景引用同步更新。**128 是刻意选的上限**：宿主对 CPU 表面有 16384 格硬限制，而显示网格固定 129×129，128 格正好与 129 个顶点一一对齐，再加密只会让网格欠采样。CFL 仍满足（`lastCflNumber ≈ 0.68`，1–2 子步）。
- **“都一样”来自唯一一组作者参数。** 足迹以前每次都用同一个 `radiusMetres=0.65`/`displacementMetres`，所以每一步都是同一圈。现在 `updateFootprint` 以「毫米量化的接触位置 + 步序」做确定性哈希，抖动半径（±28%）与压深（±40%），并按接触速度线性增益（半径 +30%、压深 +60%）。实测走廊 6 m 的 24 次接触：半径 0.616–0.959 m、压深 −0.0483–−0.1268 m，逐次不同且完全可重放。重放用同一段量化状态做种子，不引入全局随机流。
- **波形本身也带方向。** 踢水不是原地砸坑，是向前推水：`Body::interact` 的核沿冲量方向做拉伸（`stretch = 1/(1+min(0.55, speed·0.12))`），原地跺脚（无冲量）保持圆形。核仍是零净体积，质量账本不受影响（`massErrorFraction 3.6e-5`）。
- **过程中发现并修掉一个真 bug。** 拉伸核的第一版把“无方向”情形也算成投影到零向量，导致 `r ≡ 0`：足迹内所有格权重相同、内环减外环恰好抵消，**水面完全不动**。离线探针（高度图全空）暴露了它，`test:water` 没有覆盖形状所以没报。这解释了当时“水面看起来像玻璃板”的一部分现象。
- 证据图：`reports/water-realism/ripple-shape.png`（左：0.125 m 网格的方环；中：0.0625 m 网格的圆环；右：连续走动后大小不一的多个环 + 沿行进方向拉长的足迹）。
- 整链验收终于跑通：`npm run water:verify`（本轮用 `--skip-build`）240 帧 + 6 张调试视图通过，`splash` 段 `contacts 28 / spawned 28 / failed 0 / capacityRejected 0 / peakIntensity 1`，`disturbances 28` 与 `residual.eventsInjected 28` 一致；`npm run test:water` 34 109 项。

### 溅水粒子（2026-10-27 夜）

按“粒子只做离散部分”的既定方向接通了三段管道：事件带接触速度、spawn 带强度、宿主按位置生成并记账。水体权威一侧没有新增状态。

- **事件补 `impactSpeed`。** `InteractionEvent` 之前只有位移，粒子无法区分轻踩与踩实。`Body::interact` 增加可选 `impactSpeedMetresPerSecond`，只写事件、不碰任何单元；`updateFootprint` 用足迹路径已有的 `dx/dz/dt` 直接算出接触速度。传送（位移 ≥ `maximumStepMetres`）报告 0 而不是伪造 40 m/s 的落地。输入按 `[0,50]` 校验，耦合层再钳到 `maximumImpactSpeed=20`。CPU 契约新增“只有速度不同时水面与 digest 必须完全相同”的断言，防止视觉参数污染权威。
- **`SpawnParams.intensity` 只缩放数量。** 强度乘的是发射计数，不是速度、寿命或体积：CPU 参考与 GPU 调度共用同一条整数舍入规则（`llround(count·intensity)`），因此半强度在 120 个 tick 后正好发出 60 个而不是漂移；rate 分支缩放的是 phase 增量而不是每 tick 结果。子事件继承父强度（否则一次弱落水的溅射又会以满强度重放）。上限钳到 8，超出不报错而是钳制，被拒额度进入 `dropped`——这正是“钳制发生在池预算之前”的证据。非有限强度返回新的 `SpawnStatus::InvalidParameter`。强度进 digest，重放差异不会被隐藏。
- **资产 `assets/effects/water_splash.effect.json`。** 两个发射器：`crown` 锥形 40 粒（初速 2.55 m/s 向上、重力、drag 1.1、颜色随寿命淡出、尺寸收缩）与 `mist` 球形 18 粒（慢速、低重力、drag 2.2、尺寸放大）。都只引用已有的 `effects/textures/reference_glow.albedo.ngtex`，不声明 field、不带事件图，因此 GPU 与 CPU 两条路径都能装。
- **宿主按位置生成。** `--splash <id>` 打开，默认库 `build/effects/library.json`、资源根 `assets`，两者都经 `engineResolve` 以可执行文件位置兜底——`water:verify` 用项目目录当 cwd，仓库相对路径必须仍然指向仓库。生成点是事件 (x,z) 的水面高度 +1 cm；强度 `clamp(impactSpeed/2, 0.25, 1)`。实例句柄、`spawned`/`capacityRejected`/`failed`/`expired`/`stepsDropped` 全部进报告；丢弃 tick 数与水体时间欠账一样显式记账而不是静默跳过。`--splash` 与 `--effect` 共用同一个 GPU 运行时，同时给出会明确报 `NG-E-SPLASH-CONFLICT`。
- **渲染顺序修正（水花能不能被看见的前提）。** 水面 pass 采样不透明 HDR/depth 快照并把表面画在上面，而粒子此前在它之前绘制，于是“在水面之上、但在屏幕上压住水面”的水珠会被表面整片覆盖。体积烟团、旧精灵、GPU 粒子三段现在改到水面 pass 之后记录：对水面之上的粒子既是唯一能看见的顺序，也是物理上正确的顺序。水下粒子与水的互穿仍未做，报告继续不宣称。
- **画面证据（A/B）。** 用通过哈希校验的宿主构建跑两遍同帧（第 110 帧）：`--splash water_splash` 时角色身后出现一团白色水珠，`--splash off` 时同一位置只剩脚边泡沫。两份图与报告存在项目 `reports/water-realism/splash-110.*` 与 `splash-off-110.*`；开溅水那次报告 `contacts 27 / spawned 27 / failed 0 / capacityRejected 0 / peakIntensity 1.0 / stepsDropped 0`，与 `probes.water.residual.eventsInjected 27` 一一对应（同一条事件环）。
- **默认路径解析（已改，待构建）。** 从项目目录启动时，cwd 里的 `assets` 会被当成引擎资源根，导致引擎库的依赖哈希对不上并直接初始化失败。改为 `engineContent`：引擎内容先按可执行文件位置查找（`build/pond-host` → `build` → 仓库根），都找不到才退回 cwd。改动已通过单文件语法检查，但**还没进到可执行文件**——本轮每一次整包构建都被其他任务正在保存的 `engine/native/animation_features.cpp` 触发了“编译期间输入变化”的哈希守卫。
- 验证：`npm run test:water` 34 086 项（新增 61 项，`peakImpactSpeed` 3.0）、`npm run effects:cpu` 10 组 13 372 项（新增强度组）；`water:verify` 需等构建窗口恢复后再跑。

### 接触泡沫遮罩（2026-10-27 收尾）

先做泡沫而不是溅水粒子，理由是它同时解决“水面像玻璃板”和“岸线硬边”，且不动物理账本。全部在 `shaders/water_surface.hlsl` 与 `host/pond_demo.hpp`，没有新增 GPU 资源、没有改 ABI。

- **两种来源，都不是第二个求解器。** 岸边接触由“足迹边界距离 + 边缘噪声扰动 + 极浅水柱”合成：先试的纯深度带在平坦池底上只有一格宽、且被水面下垂的深度测试裁掉，实际只剩 2 像素的描边，因此改成 0.13 m 亮线 + 0.42 m 碎沫两层，并对边界距离做噪声扰动，避免成圈刷子。搅动泡沫来自 CPU 求解器已有的表面量。
- **接触信号换成“偏离静水面高度”。** 水平速度在落脚点接近 0（脚是把水往下压，不是往旁边推），所以 `query().velocityX/Z` 在脚印处没有信号。改用 `|surfaceHeight - stillHeight| / 0.03`，同一项也覆盖波峰，天然是“白水在破碎波峰上”。
- **泡沫有衰减记忆。** `PondDemo` 保留每个水面顶点的泡沫状态，按仿真时间以 0.45 s 时间常数衰减，并做一次 3×3 取大：单次落脚只覆盖一两个求解格，不扩张就成了一道划痕而不是被搅动的水。该状态是纯呈现量，不写回 `Body`，同一 tick 两次取表面不会重复衰减。
- **阈值取自资产。** 噪声与花纹用两段值噪声（细节段按像素足迹淡出，防闪烁）；阈值用资产的 `foamThreshold`，但其 35% 起跳——资产里那个值描述的是持续白水，落脚只是瞬变。
- 验证：`mode 5` 调试图里 B 通道现在是“沿岸一圈 + 身后一条尾迹”，静水中部保持干净；`npm run test:water` 34 025 项、`npm run water:verify` 240 帧全部通过。

### 渲染路径恢复与可分离验收（2026-10-27 晚）

此前一轮的验收证据其实是失败的：`water:verify` 在 CPU 专项链接阶段就中止（`updateFootprint` 未链接 `coupling.cpp`），宿主运行到首个水帧即报 `NG-E-WATER-RIPPLE: create upload (0x887A0005)`，水通道一帧都没有画出来；17:57 的截图来自更早的构建。已修复并复验：

- **专项链接。** `water-realism.mjs` 补上 `engine/native/water/coupling.cpp`，CPU 契约恢复到 34 025 项检查。
- **设备移除的真实原因。** `renderer/water_ripple.cpp` 的 `Com<T>` 可拷贝，`makeField` 按值返回后临时对象析构释放了唯一引用，`height[]/velocity[]` 变成悬垂指针，后续建视图与资源命中已释放对象导致设备移除。改为不可拷贝 + 移动语义，`makeField` 改写为出参填充。这是水通道此前完全不可用的根因。
- **错误契约。** `NG-E-WATER-RIPPLE` 现在附带原始 HRESULT，资源创建失败不再只有调用点标签。
- **调试视图可达。** `--water-debug` 上限由 5 改为 6，残差场视图可选中；`validateWaterFrame` 本来就允许 0..6。
- **可分离静帧。** `water:verify` 除主静帧外，在同帧号（110）额外采集 1..6 号调试视图到 `reports/water-realism/aov/`，逐个断言成功并写入 `acceptance.json` 的 `debugViews`；`--skip-aov` 可跳过。方案要求的“分离查看法线、厚度、反射、透射、波纹、泡沫”由此成为每次验收的固定证据。
- **残差足迹原点。** `PondDemo::surface` 把水体中心当作残差原点发布，而顶点与计算两段都按“原点 + 局部坐标”解释，等于把整片残差场平移了半个范围：交互足迹落在场的边缘，半个水面采样到钳制边界。改为发布足迹角点，并在 CPU 契约中加入“原点等于角点”“原点加半范围回到中心”“事件 UV 落在 [0,1]”三项断言。
- **残差振幅与零均值核。** 残差原先直接把权威位移（-0.09 m）注入可见高度，而网格本身已经绘制了这份位移，等于把同一份水抬两次并立刻顶到 0.08 m 上限；截断在 `r2=6.25` 的 LoG 核还残留 `e^-3.125` 的尾部积分，会整体抬升水面。改为：注入乘 0.35 视觉增益、上限降到 0.03 m、核补上尾部常数项使支撑域内严格零均值、子步稳定界收紧到 0.35（2D 五点格式在 0.7 附近只有边缘稳定）、首帧用 `grid.w` 重置标志把两对 ping-pong 纹理写成静水（`ClearUnorderedAccessViewFloat` 在未绑定描述符堆时会被静默丢弃，改用计算通路重置）。

**结论性证据：残差目前没有正确接入可见表面。** 上述求解器改动后，第 2、8、96 帧的输出与改动前逐字节一致，而关闭残差对几何位移与着色法线的影响后，同一帧水面从“整体褶皱噪声”变为平静水面。因此残差纹理的内容与求解输入不一致（不是求解常数问题），当前以 `residualAffectsSurface=false` 显式关闭其对可见表面的影响，仅保留 6 号调试视图采样；CPU 高度场与解析风纹仍在。定位该项需要给残差场加一次性回读诊断，属于下一步。

复验入口：`npm run test:water`（34 025 项，通过）、`npm run water:verify`（240 帧水通道、240 次残差派发、27 次事件注入、786 万三角、6 张调试视图，通过）。逐字节一致的对照与关闭残差后的静帧分别留在 `reports/water-realism/probe*-*.png`。

### 前序增量

- 新增 `renderer/water_draw.*`、`shaders/water_surface.hlsl`：129×129 共享水面采样、HDR 颜色与不透明深度快照、视角 Fresnel、深度吸收/散射近似、前景折射拒绝、屏幕空间反射与程序化天空回退、梯度法线和解析细波。此项尚待实际画面验收。
- **GPU 局部波纹残差（阶段 3 首项）。** 新增 `renderer/water_ripple.cpp`、`shaders/water_ripple.hlsl`、`kWaterRippleCS`：256×256 有界线性波场，按 CPU 表面深度调制波速并对干格清零，反射岸界加指数吸收带，事件用零净体积 Laplacian-of-Gaussian 核注入。60 Hz 帧长超过 3.1 cm 网格的显式稳定上限，因此按 `dt / (0.6·dx/c)` 子步进 1–4 次，而不是把波速钳低。残差只进入几何位移与着色法线，不向玩法回读。
- `WaterRippleEvent` 事件契约：`WaterSurfaceFrame.events` 为最近 32 条带绝对 tick 的环形历史，`WaterRipple` 按 tick 去重，因此同帧两条渲染路径读到相同事件也不会重复注入；时间线回退时 CPU 清空环形、GPU 重置游标。
- `engine/native/water/Body::interact`：局部零净体积位移和明确单位的水平冲量，保留已有动量与初始质量基线；已通过水专项 CPU 检查。
- `Game::observeFixedTicks`：只读呈现观察接口，逐个实际 120 Hz 游戏步调用；水体不再依靠每渲染帧末尾猜测角色轨迹。该接口本身不赋予水体玩法权威。
- 修正 InteractivePond 的池底/水材质 ORM A 通道为 0，保留 imagegen 原始素材；项目源数据和烘焙结果均在项目目录内。
- **CFL 预算与数值故障诊断。** `Body::step` 的实际子步长不再超过 CFL 界：所需子步超过 `maxSubsteps` 时只推进预算内可稳定覆盖的时间，剩余时间记为 `timeDebtSeconds` 并由后续 tick 偿还（每 tick 最多补一个 `dt`），超过 0.25 s 的部分丢弃并计入 `droppedSeconds`。`Diagnostics` 新增 `lastCflNumber`、`timeDebtSeconds`、`droppedSeconds`、`sanitizedCells`，宿主 `pondDemo` 报告同步输出。非有限单元清零仍作为运行时保护，但不再替代稳定性证据。
- 专项入口：`npm run test:water`、`npm run water:verify`。CPU 专项含水资产 4 项，并验证质量/冲量、边界、非法输入、扰动演化和连续水面确定重放；新增事件契约检查（事件数等于权威交互数、tick 严格递增、半径/位移有界、位置在足迹内、重放逐条一致）。新增 0.25 s 超预算大步长（实测欠账 0.048 s 并完整偿还）与 9×10⁴ N·s 剧烈冲量（`lastCflNumber` 恒 ≤ 1、无 NaN、重放一致、丢弃 0.175 s 显式记账）用例。扰动 480 tick 的质量误差比例约 0.0000363。未运行全量测试或 CI。
