# 真实水体系统：现状诊断与实施方案

日期：2026-10-27。本文是基于当前源码和公开一手资料的设计分析，未实现下列新增能力，也未重新执行运行验收。延续现有 `PARTICLES-FIELDS-CLOTH-WATER-PLAN.md` F 阶段，优先完善 InteractivePond；不添加植被，复用现有人物。

## 1. 当前画面失真的具体原因

1. **材质通道错误。** 实际读取项目烘焙文件：`pond_water.orm.ngtex` 首像素为 `[255,88,0,255]`，`pond_bed.orm.ngtex` 为 `[255,230,0,255]`。`shaders/material.hlsl` 将 ORM 的 A 通道用作 emissive，默认发光为 `albedo * emissive * 2`。两种材质因此带有非预期自发光，造成发亮、颜色扁平。这是原型制作中的错误，后续应先修正源图与重新烘焙，并检查运行时读取结果。
2. **没有连续水面。** `host/pond_demo.hpp` 将 8 米水面绘制成 16×16 个独立薄盒，每块约 0.5 米，只平移盒体，没有用高度梯度改变表面法线。32×32 CPU 求解状态也被进一步降采样。细波既不能形成连续轮廓，也不能形成对应的反射变化。
3. **通用表面材质缺少水介质光路。** 当前演示使用普通材质，没有水专用的透射、厚度、吸收、折射、反射组合。普通材质透明和已有环境高光不等价于水渲染。
4. **交互输入属于测试钩子。** 角色移动约 0.4 米后在两个固定方向邻格间移水；`Body::setDepth` 会清除该格水平动量并修改守恒初始基线。它适合作者设置初始条件，不适合持续的物体排水、冲击与尾流。当前事件在整次 Game 更新后发生，也没有精确映射到各个固定 tick。
5. **缺少环境联系。** 岸边为直角矩形、底床平坦，没有连续浅滩、岸线湿润或真实深浅变化；水花、接触泡沫与水下相机未接入。
6. **现有验收不足。** “运行 240 帧、触发 18 次事件”只能证明代码路径工作，不能证明画面自然、波纹正确或双向物理成立。

现有 CPU 浅水模型、资产校验、查询、浮力估算、共享场投影可以复用。还需复核稳定性：`Body::step` 达到 maxSubsteps 后继续以 dt/substeps 积分，`cflClamped` 只作标记，不能据此宣称超预算时仍满足 CFL；非有限数状态清零也不能代替数值故障诊断。

## 2. 成熟实现值得采用的结构

- Unreal 的 Single Layer Water 将水作为专用介质渲染，利用水下场景颜色和深度处理折射、吸收、散射；反射另行组合，水有专门的渲染阶段。其公开实现的阶段顺序不能直接照搬为本引擎渲染图。
- Unreal 的水面采用独立的水域/样条和带 LOD 的连续网格；其浮力使用球形代理点来近似物体体积，并提供阻力。代理模型需要明确误差与支持范围。
- Unity HDRP 的公开技术介绍采用频段分离的 FFT 波、顶点位移、细节波纹，以及独立的局部变形、泡沫、流向和查询模块。文章明确区分水面变形与三维液体/飞溅模拟，不应将这些功能混称为同一个求解器。
- NVIDIA GPU Gems 展示几何波与动态法线波分开表达的思路。小于网格可表达波长的细节应转移到法线，并处理采样和抗锯齿。

共同启示是分开建设水域数据、表面几何、光学、模拟与对象交互，再使用同一组空间/时钟合同连接。

## 3. 推荐的系统边界

### 水域与创作

增加正式 WaterBody 场景组件，引用已有水资产；包含边界多边形或河道样条、world transform、水位、底床/深度、流向、介质参数和预算。waterBodyId 属于对象身份，不能作为可随意插值的场通道。重叠水域必须有明确选择规则。

替换 `.enabled` 文件和宿主中硬编码的项目演示逻辑。编辑预览、运行、保存、热重载和发布读取同一份水域数据。修改几何/后端时显式重建，材质更新可保留模拟；失败继续旧有效状态。移除水体或重载其他场景时完整释放实例。

### 连续几何与法线

8 米水塘首先使用共享索引的连续三角网格，128×128 顶点可作为原型起点，最终按近景轮廓和预算选择。网格分辨率不强迫等于求解分辨率；插值不会凭空创造物理细节。

顶点读取水面高度，法线由同一高度场梯度生成：`normalize(-dH/dx, 1, -dH/dz)`；再正确组合高频细波法线。使用世界空间坐标保证跨网格块连续，法线纹理使用线性数据、可重复边界与正确 mip。大范围水体随后引入四叉树或 clipmap，处理 LOD 边界、位移包围盒和裂缝。

### 专用水光学

增加水深/水面法线/水域索引数据和单独 WaterPass。首版约束每条相机视线只处理一个主水面，保留以后处理多层水的扩展空间。

- 空气到水的 IOR 取约 1.333 时，垂直入射 F0 由 `((n1-n2)/(n1+n2))^2` 得约 0.0204；随视角变化混合反射和透射。
- 依据折射光路厚度处理 RGB 吸收/散射。单色 albedo 或统一 alpha 不能代替深浅关系。使用 `T=exp(-sigma_t*d)` 作为均匀介质透过率的近似起点，区分吸收与散射来源。
- 折射读取不含当前水面的线性 HDR 场景颜色；重建几何深度并拒绝前景泄漏。离屏、无背景或深度不可信时有明确回退。
- 小水塘优先验证平面反射，能提供稳定的岸边/人物倒影；根据实测成本降低分辨率、更新频率并裁剪反射相机。平面反射不能精确匹配强位移曲面。SSR 是后续质量档，离屏必须回退到环境；DXR 反射单列扩展。
- 水下散射、焦散投射和岸线湿润在基础光路成立后加入；平静池塘不应到处是白色泡沫。

现有渲染器已有 FP16 颜色目标、深度 SRV、环境高光和透明片段合成，具备部分输入基础。但水处理需要显式保留不透明 HDR 场景快照、扩展描述符/资源状态/尺寸重建，并改造与烟雾和透明物的合成关系。当前合成阶段还执行雾与色调映射，不能直接把最终 LDR 画面作为水折射输入，也不能重复积分雾或水介质。普通透明片段排序本身不能解决折射后背景依赖。

### 模拟与交互

首版保留 CPU 权威水位/粗浅水，增加 GPU 局部波纹残差。最终可见高度为 CPU 基础表面加视觉残差及受限风细波；限定频段并统计可见高度与物理查询的偏差，避免重复叠加同一组低频波。GPU 细节不向玩法提供同步回读。

输入改为固定 tick 的 WaterInteractionEvent，包含水域、位置、半径、相对速度、方向、排水变化和冲量；进入、持续移动、离开分别处理。按足部/胶囊或刚体代理足迹将输入平滑分布到多个格点，避免固定朝 +X 移水和帧率相关触发。为动量与排水建立专用接口，保留现有质量账本；纯视觉波纹不宣称拥有权威水量。

GPU 波纹可从 128×128 有界高度场开始，使用浅水深度调节波速和干湿遮罩，验证障碍、开放/反射边界、衰减与采样稳定性。需要真实水流、冲刷、淹没时，再移植守恒浅水的 GPU 视觉后端；不得将线性波纹当作完整浅水求解。海面远景扩展 FFT 多频段；容器倒水、翻卷和局部三维液滴另设有限容量的 PBF/FLIP 等后端，不能用高度场表示同一点多层水。

浮力先接入多点体积代理，将浮力和相对水速阻力施加到物理系统，在代理位置产生力矩；角色另做涉水阻力与状态切换。双向反馈按固定顺序将排水/动量投影到 CPU 模型，GPU 消费相同事件产生细节。CPU 与 GPU 结果分别验证，不依赖 GPU 回读推进权威物理。大飞溅先用事件驱动粒子，独立于守恒水量；需要水量交换时显式记账且只转移一次。

### 资产职责

imagegen 适合岸石、泥沙、泡沫/湿润遮罩等美术素材。直接生成的紫色图不能被默认当成物理正确、无偏且可积分的法线场。主水面法线应来自模拟高度或有约束的程序化波谱；生成法线可在检查、归一化和抗锯齿后作受控微细节。资产烘焙要校验通道语义、线性/sRGB、边界连续性、法线偏置和 mip，非发光 ORM 的 A 通道需符合本引擎契约。

## 4. 实施顺序与阶段验收

1. **基础材质与连续表面。** 修复自发光，移除盒体，接入位移/梯度法线与正式水体实例。验收：倾斜视角无拼缝，静水不自发光，法线与位移一致，编辑/运行视图读同一实例。
2. **可信的静态水光路。** 加入折射、水厚度、吸收/散射、Fresnel、反射及回退。验收：浅处可见池底，深处自然衰减，掠射角反射更强，人物和岸边倒影稳定，前景几何不被错误折入。
3. **可信的运动。** 固定 tick 交互输入、GPU 波纹残差、局部水花和泡沫。验收：落水产生向外传播的环波，移动产生方向正确的尾迹，停止后衰减，改变渲染帧率不改变 CPU 事件账本；开放和封闭边界行为分别成立。
4. **可信的物理与水下。** 浮力、阻力、力矩、角色状态、水线与湿润。验收：规定箱体稳定漂浮，静水无无源能量增长，CPU/视觉表面偏差在约定范围内；相机过水线无闪烁，烟/玻璃/水花合成有明确限制。
5. **生产化及扩展。** 补齐保存/恢复、热更、发布、撤销、设备重建和预算分档；通过后再扩展河流、海面、局部三维液体。超预算的回退不改变 CPU 权威数据。

逐阶段保留静水、涉水、入水冲击、漂浮物、岸线、低角度反射、相机穿水线的固定镜头与视频。视觉验收必须能分离查看法线、厚度、反射、透射、波纹和泡沫；数值检查覆盖质量、动量/能量输入、CFL、干湿与来源身份。记录分辨率、GPU、质量档、平均及高分位帧时间，不凭参考引擎宣传数字承诺本工程性能。

后续验证入口按约定放 `.incrementalTesting/simulation/` 和 `.incrementalTesting/rendering/`，新增时同步命令索引、package 与 CI 范围。本次仅新增分析文档，未新增验证命令或运行全量测试。运行项目继续位于 `Documents/nativeEngineProject/InteractivePond`。

## 5. 下一阶段：流动、落差与障碍（2026-10-27 追加）

当前水塘是“一池静水 + 交互环波”。要更像水，缺的不是更多着色，而是三种**水与环境的交换**。下面按“改动面 / 现有基础 / 验收”排列，前两项可以在不新增后端的前提下完成。

### 5.1 障碍与岸石（优先级最高）

现状：求解器只在**区域边界**做反射，池塘里的石头、台阶、树干对水**完全没有影响**——波会直接穿过去。这是“像一张纸”的最主要原因之一。

- 做法：资产增加 `solid` 掩码（每格 0/1，可由场景碰撞体或高度图烘焙）。面通量在 solid 侧一律置零，压力项回填为中心格静压（与现有闭边界同构），于是波在石头周围自然绕射、反射，并沿石头背面留下静水区。
- 泡沫：solid 相邻格是天然的“拍岸白水”位置，比现在按矩形足迹边界画泡沫准确得多（同时解决岸线仍贴矩形的问题）。
- 额外成本：CPU 每步多一次掩码查询；GPU 残差场复用同一掩码（`depthField` 已按格上传，可扩成 rgba：深度 + solid）。
- 验收：单块石头后出现阴影区与绕射；质量账本误差不变；确定性重放逐字节一致。

### 5.2 水流（河流 / 泉眼）

现状：资产已经解析 `boundaries.inflow/outflowCubicMetresPerSecond` 与 `openBoundaries`，但求解器**没有消费**它们；水塘里没有一处水在“往一个方向走”。

- 做法一（最小）：把 inflow 实现成边界格的质量+动量源，outflow 用辐射边界；水塘变成“活水”，泡沫、漂浮物、粒子都能读出 `velocityX/Z` 并被带走。守恒账本把注入量单列（`addedCubicMetres` 已有字段）。
- 做法二（更像河）：增加一个外部流速场 `flow(worldXZ) -> (u,v)`（常量/样条/贴图三种来源），以源项形式进入动量方程，而不是替代它。静水仍然静，河段整体在流。
- 视觉：表面细波沿流向拉长（各向异性风纹已经有了雏形，把方向从资产常量改成流速方向即可）；泡沫被平流而不是原地衰减。
- 验收：注入 N m³/s 后水位稳定在水位线上；示踪（泡沫）在固定时间后到达下游指定区域；关闭 inflow 后水塘重新静止。

### 5.3 落差与瀑布

现状：`BathymetryType::Slope/Basin` 已声明，`bedAt()` 支持倾斜/盆形底床；但**高度场无法表示自由下落的水**，硬做只会得到一条“斜坡上的滑梯水面”。

- 诚实的分工：跌水本身是**独立的视觉系统**（薄片网格或粒子），落点用水池求解器接收**持续扰动**（把 footprint 的单次事件换成“按流量注入的环形扰动”，复用 `Body::interact` 的零净体积核）。
- 需要的三件：① 跌水口的几何（水面在此处被“剪断”）；② 落点处的连续扰动 + 泡沫源；③ 溅射粒子（本轮已通的 `--splash` 管道可直接按流量触发，无需新区间）。
- 验收：落差处的水平面不再连续（不会被高度场强行连起来）；落点泡沫与扰动强度随流量单调变化；关闭水源后水池回到静水。

### 5.4 让波动本身更真（不改架构）

- **双频段**：毛细波（短、衰减快）与重力波（长、传播远）分开注入，落水先出细碎高频、再被子波接管。当前只有一个半径的单一环。
- **振幅相关的波速**（Stokes 一阶修正）让波峰更尖、波谷更平，环波不再是正弦圈。
- **按深度衰减**：浅水区波速低、破碎早，岸线附近自然出现“推上去又退回来”的碎波。
- **GPU 残差重新接入**（子厘米细节）：现在 `residualAffectsSurface=false`，需要先给它加一次性回读诊断，定位“纹理内容与求解输入不一致”的环节。

### 5.5 光学上最划算的两项

- **真实水深吸收**：现在吸收按屏幕空间厚度近似；改成 `bedAt()` 与水面高度之差后，浅滩会真的透出卵石、深处真的发暗（池底平坦这件事也会立刻显得合理）。
- **池底焦散**：把水面法线的拉普拉斯投影到池底作为亮度调制，成本低、观感提升大，且与已有的法线/厚度调试视图天然对齐。

顺序建议：5.1 障碍 → 5.5 水深与焦散 → 5.2 水流 → 5.4 双频段 → 5.3 瀑布。前两项做完，“水”与“地面/石头”的关系就成立了；瀑布放在最后，因为它是唯一需要新增视觉子系统的一项。
