## 1. 目标、范围与成功标准

### 1.1 用户要解决的问题

1. 角色交互后的波纹呈方形或菱形扩散，明显暴露网格。
2. 每一步像播放同一段波纹动画，大小、轮廓和节奏重复。
3. 角色慢走、奔跑、停止、转向、跃入水中的反应缺少区别。
4. 水体需要具有真正的流动方向，能沿地形由高向低流。
5. 水流遇到石头、岸壁和动态物体后，应改变路径并产生合理尾迹。
6. 水从高处落下时，应有连续水片、边缘破碎、落点冲击、泡沫和水雾。
7. 提升真实感时，应保留质量守恒、数值稳定、确定性和可控性能。

### 1.2 最终期望的可见行为

- 安静池塘：风驱动的低幅细波，不会自行出现持续强烈泡沫。
- 轻踩：脚掌附近短促、较弱、逐渐消散的小波与少量水滴。
- 涉水行走：左右脚接触产生不同位置和大小的扰动，波相互干涉。
- 奔跑：接触更强，有方向性的波头与尾迹，停止后余波继续传播。
- 跃入水面：更强的垂直冲击、短时凹陷、环波、喷溅和泡沫。
- 河流：主体速度场稳定推进，泡沫与漂浮物沿流向移动。
- 石头：迎水侧抬升、两侧分流、背水侧尾流；水不会直接穿过实心障碍。
- 瀑布：上游流量连续进入下落段，再进入下游，视觉粒子数不决定水量。
- 不同镜头、帧率与画质设置：视觉细节可以变化，玩法质量账本不能随之变化。

### 1.3 不作为首轮交付承诺的内容

- 全场景三维高分辨率液体模拟。
- 全海域高精度破碎浪与翻卷浪。
- 仅凭新贴图就实现真实水动力。
- 对所有硬件承诺固定毫秒数。
- 把任意桥洞、悬垂和多层积水压缩成一个高度场后仍保持几何正确。
- 未经验证就声称完整实现某篇论文、FLIP、APIC 或 PBF。

## 4. 已有实现与未完成内容

### 4.1 本次核查时存在的实现

- `Body` 支持 `Analytic`、`Shallow`、`Spectrum` 后端身份；三者行为不同，不能都当成守恒液体。
- `Shallow` 使用 CPU 有限体积浅水参考实现，包含床高、水深、水平状态与质量诊断。
- 具有静水、扰动、CFL 子步、时间债务、丢弃时间和非有限状态诊断。
- `Body::interact` 注入零净体积的局部高度扰动与水平冲量。
- 步距触发已有确定性半径/强度变化及速度相关变化。
- CPU 交互核已有沿水平冲量方向的拉伸。
- 有涉水深度、移动速度与跳跃相关影响。
- `coupleBox` 已有代理采样浮力、相对水速阻力、浮心转矩与唤醒判断；`Game` 中存在调用。
- 这些代码存在，不代表所有刚体、姿态、动态水域和双向耦合情形均已验收。
- 宿主生成连续 CPU 水面网格，并发布水体交互事件。
- GPU 有界细波纹层存在，当前分辨率常量为 256。
- 水面有专用光学绘制及多个调试视图。
- 喷溅可由记录的水体接触触发，已有生成、过期、失败和容量诊断。

### 4.3 已修复问题，后续不能回退

1. 子步常量曾重复写同一上传地址，后续 dispatch 参数覆盖先前参数。
2. 上传资源曾未按在途帧隔离。
3. 首帧重置曾吞掉同帧注入。
4. 事件传输曾丢失方向和拉伸信息。
5. 单一 GPU 接触核缺少轮廓差异；现有稳定哈希控制双频带变化。
6. 长条域曾按相同格距计算世界距离与斜率。
7. 图形描述表第二个范围曾默认偏移为 0，使 `t5` 错读 `t0` 颜色纹理。
8. 独立 GPU 求解正确不能证明实际绘制绑定正确；已有真正绘制回读测试防止回归。

历史事件 ABI 为 32 字节。新增字段时应同步 C++、HLSL、结构步长、上传与验证，不能只修改一端。

### 4.4 历史证据的正确使用

2026-10-28 曾通过 CPU 34,160 项断言、6 项 JS 合同、GPU 65,953 项断言以及 240 帧实景检查。历史 GPU 独立径向测试的四重角向偏差约为 0.000344341。

这些数字是当次夹具和构建的结果，不是未来阶段的承诺，也不是完整画面的真实度评分。历史验收使用独立源码快照，不能代表快照之后其他模块的修改。复现说明见当天记录。

## 5. 推荐系统结构与权威边界

```text
场景地形 / 岩石几何 / 水域资源 / 局部入口出口
                         |
                         v
          CPU BulkWater：水深、床高、水平状态
            |            |                |
            |            |                +--> 玩法查询 / 浮力阻力
            |            +--> 瀑布水量转移账本
            v
       固定 tick 水面快照与速度场
            |
角色脚掌 / 入水 / 刚体接触 --> 交互事件
            |                    |
            v                    v
      GPU 细波纹传播与平流     喷溅 / 水雾 / 泡沫来源
            |                    |
            +----------+---------+
                       v
        水面位移、法线、泡沫、折射、反射、吸收
```

图中 `BulkWater` 是职责名称，不要求新建同名类。优先扩展当前 `Body` 与现有模块。

### 5.1 权威状态

CPU 保存水体对玩法有意义的水量与动量。GPU 视觉降级、粒子丢帧、截图或相机变化均不能改变这些状态。

若未来迁移到 GPU 权威求解，必须单独设计同步、查询时延、确定性与失败恢复；不能顺手把当前视觉残差改成玩法权威。

### 5.2 避免两层重复计算

- CPU 已经表达的低频扰动，不应在 GPU 再完整注入一遍。
- 明确低频主体、局部细节与光学法线各自承担的尺度。
- GPU 残差应有单位、增益、限幅与诊断。
- 每一步随机波形不能同时使 CPU 与 GPU 独立选择两个互不相关的接触方向。
- 浮力与水面显示可存在细节差异，但需要说明差异上限，避免物体浮在明显错误的高度。

## 6. 数学、单位与坐标合同

### 6.1 必须统一的量

| 符号/量 | 单位 | 说明 |
| --- | --- | --- |
| `x, z, b, h, eta` | m | 水平位置、床高、水深、自由表面高度 |
| `u, v` | m/s | 水平流速 |
| `dt` | s | 固定模拟步或受约束的视觉子步 |
| `Q` | m³/s | 体积流量，不是每帧深度变化 |
| `V` | m³ | 水量 |
| `rho` | kg/m³ | 密度，清水近似值用于尺度一致性 |
| `J` | N·s | 积分冲量，不是连续力 |
| `F` | N | 力，需要乘时间才得到冲量 |
| `h*u, h*v` | m²/s | 浅水守恒变量；不能直接称为总物理动量 |
| `rho*A*h*u` | kg·m/s | 单元水平物理动量，其中 `A` 为有效水平面积 |
| 泡沫覆盖/湿润度 | 无量纲 | 需定义范围及其衰减时间常数 |

需审计现有参数的隐含单位。例如“水平速度 × impulseScale”作为 N·s 输入时，比例参数实际上承担单位换算，不能仅凭变量名认为它是无量纲物理模型。

### 6.2 坐标

- 明确场景世界坐标、以水域中心为原点的局部坐标，以及纹理左下/左上约定。
- 当前水体中心原点与 GPU footprint 角点原点不是同一概念。
- 纹理格距分别取 `dx = extentX/Nx`、`dz = extentZ/Nz`。
- CPU 单元中心、表面顶点和 GPU texel 中心应分别定义映射。
- 带平移的水域测试至少覆盖非零 X、Y、Z。
- 旋转水域若不支持，应明确拒绝，不应悄悄按轴对齐解释。

### 6.3 基础守恒关系

忽略障碍占据时：

```text
eta = b + h
V = sum(h_i * A_i)
dV/dt = Q_in - Q_out + Q_external
```

移动障碍使自由面积变化时，需要显式定义 `A_free` 或等价的体积表示，不能继续无条件使用完整单元面积。

浅水形式的参考方程：

```text
∂h/∂t + ∂(hu)/∂x + ∂(hv)/∂z = S_h
∂(hu)/∂t + ∂(hu² + g h²/2)/∂x + ∂(huv)/∂z = -g h ∂b/∂x + S_x
∂(hv)/∂t + ∂(huv)/∂x + ∂(hv² + g h²/2)/∂z = -g h ∂b/∂z + S_z
```

这些方程用于约束设计，不要求推翻现有离散方法。地形源项与静水压通量必须保持平衡；“斜坡床上自由表面水平且静止”可以是合法静水，不应凭坡度强制制造流动。

### 6.4 稳定性与耗散

- CFL 应结合 `|u| + sqrt(g*h)`、`|v| + sqrt(g*h)` 和两轴格距计算。
- 不得把一维上限直接套入二维格式，也不得给所有格式使用同一固定系数。
- 达到子步预算时，记录时间债务或明确丢弃的时间，不能偷偷使用不稳定大步长。
- 干湿交界需要正水深、正性保护和低水深速度处理。
- 摩擦、黏性、边界吸收和数值扩散是不同机制，应分别诊断。
- 半拉格朗日平流可以用于视觉标量，但不自动保证质量守恒。
- 视觉限幅是最后的边界保护；持续撞限幅要报告，不能把它当成稳定性证明。

## 7. 交互事件、随机化与脚掌接触

### 7.1 先修复事件语义

当前去重依赖 tick。未来同一 tick 可能同时存在左右脚、多个角色和刚体接触，必须审计以下情况：

- 同 tick 多事件是否全部处理。
- 一批事件超过 GPU 单次容量后，是否错误地把游标推进到尚未交付的事件之后。
- 重复提交同一水面快照是否重复注入。
- 时间线回退、场景重载和新水体是否残留旧波。
- 事件序号回绕与存档恢复如何处理。

建议使用水域内单调 `eventSequence` 加 `timelineEpoch`；`tick` 表示发生时间，不承担唯一身份。也可以选择更合适的现有 ID 机制，但必须有明确合同和测试。

### 7.2 建议事件合同，尚未实现

```text
WaterInteractionEventProposal
  timelineEpoch, eventSequence, simulationTick
  waterBodyId, actorId, contactId
  kind: touch / footPlant / drag / landing / rigidImpact
  positionWorldMetres
  contactNormalWorld
  footprintMajorMetres, footprintMinorMetres, orientation
  relativeHorizontalVelocityMetresPerSecond
  relativeNormalVelocityMetresPerSecond
  displacedVolumeProxyCubicMetres
  horizontalImpulseNs
  deterministicSeed
```

这是语义清单，不要求将全部字段塞进现有 32 字节 GPU 结构。CPU 事件可较丰富，GPU 使用紧凑、显式版本化的派生事件。对象 ID 使用已有稳定标识，不能使用跨运行变化的裸指针。

### 7.3 脚掌接触状态机

```text
Dry -> SurfaceCrossing -> SubmergedContact -> Dragging -> Leaving -> Dry
```

- `SurfaceCrossing`：脚部轨迹穿过水面，结合上一 tick 与当前 tick 插值定位。
- `SubmergedContact`：脚掌持续浸入，不应每帧重复生成落脚脉冲。
- `Dragging`：持续移动时沿距离积分生成尾迹，限制采样间距和每步预算。
- `Leaving`：脚掌出水可有较弱拉升与滴水，不能自动复用入水强度。
- 站立姿态抖动需要滞回，防止接触状态每帧切换。
- 瞬移和动画重置应清理状态；不能把跨地图距离当作高速划水。
- 真实脚掌数据不可用时保留当前步距逻辑作为明确标注的降级路径。

### 7.4 接触速度与能量

使用相对水速，而不只是角色世界速度：

```text
v_relative = v_contact - v_water
v_normal = dot(v_relative, surfaceNormal)
v_tangent = v_relative - v_normal * surfaceNormal
```

接触能量代理可参考有效质量与法向相对速度平方，但应校准与限幅。脚掌有效质量不同于整个人物质量，不能无条件把人物全身动能注入每只脚。

初期可以保留美术控制的经验模型，但要明确哪些参数是物理量、哪些是视觉增益，并通过动作强度排序验收。

### 7.5 随机化分层

| 层级 | 可以变化 | 约束 |
| --- | --- | --- |
| 接触级 | 半径、凹陷幅度、椭圆比例、小角度偏转 | 围绕接触尺度与强度变化 |
| 波包级 | 频带权重、波宽、短尾迹长度 | 有界，不额外注入未记账水量 |
| 喷溅级 | 水滴尺寸、角度、寿命和分布 | 与接触强度相关，受实例预算限制 |
| 环境级 | 风波相位、方向散布、阵风 | 时间连续，不能逐帧换随机图案 |

种子建议来自水体资产 seed、稳定角色 ID、接触 ID 和事件序号。每种用途使用独立随机通道，避免新增一个水滴随机数就改变所有后续脚步波形。

建议先调试半径约 ±10%～30%、幅度约 ±10%～40% 的有限变化；这些范围是可调初始建议，不是当前源码合同。保留低幅均值，避免因非线性参数映射使长期能量持续偏高。

## 8. 波纹传播与方形痕迹专项

### 8.1 分层定位

1. 事件位置是否正确，原点是否相差半个水域。
2. 初始注入核是否已经方形，还是传播后才出现四重方向结构。
3. CPU 低频高度与 GPU 残差各自的径向对称程度。
4. 水深采样、干湿掩码是否有台阶或矩形裁切。
5. 长条域是否错误共用两轴格距。
6. 几何网格、法线插值和高光是否放大了不可见的微小误差。
7. AOV 是否读取真正的波高，而非场景颜色、深度或未初始化纹理。

### 8.2 后续改进原则

- 保留现有 GPU 九点细波纹格式的稳定性与边界测试。
- 如优化 CPU 轴向离散，应另做守恒、正性和静水平衡证明，不能直接把九点拉普拉斯替换进有限体积通量。
- 更高分辨率只作为有预算的数据点，不是唯一方案。
- 可评估更高阶重建、限制器与较低方向偏差格式，先比较相同成本和相同网格下的结果。
- 旋转接触方向后，波形应相应旋转，而不是仍沿世界 X/Z 方向展开。
- 加入主流后，细波纹应在移动背景中传播，并与岸线、深度变化相容。
- 色散扩展放到基础传播与平流通过之后，不要用多频正弦叠加冒充完整色散求解。

### 8.3 指标与观察窗

- 在均匀平底、无风、无流、远离边界的夹具中测量径向波。
- 将波前距离、相位或能量按角度分箱，比较轴向与对角方向。
- 可保留现有四重角向偏差指标，并同时查看波高图、剖面和半径误差。
- 避免只在波还没传播时验收，也避免只在撞到矩形边界后用径向对称要求判失败。
- 方向性脚步不应被要求圆形对称，应与方向变换后的参考比较。

## 9. 局部入口、出口与地形水流

### 9.1 位置化流量合同

建议增加入口/出口区域、流量、方向、有效开口宽度和启用时段。实际字段名需在资源设计阶段决定。

一次子步中，入口体积应为 `dV = Q*dt`。若分配到多个单元，权重需按有效面积归一化，避免分辨率改变后流量改变。

同时注入与入流水速一致的水平动量。只加深度而不定义入流动量，会造成错误水堆或与预期不符的扩散。

出流不得抽取超过可用水量；应记录请求、实际出流和受限量。开放边界应明确用于自由出流、水位约束还是指定通量，不能把三者混为一谈。

### 9.2 地形接入

1. 定义床高来源：资产公式、采样高度图或场景碰撞几何。
2. 世界坐标投影到水域局部网格。
3. 记录采样精度、最小特征尺度、无数据区域与资源哈希。
4. 静态河床构建可缓存；变更相关几何或水域变换时使缓存失效。
5. 桥面和洞穴应按场景语义处理，不能把最高三角形一律当作河床。
6. 改变床高时显式处理被占据的水体积，不能靠重新计算深度静默丢水。

### 9.3 随流搬运

泡沫、浑浊度和视觉细波使用同一空间/时间基准下的速度快照。快照应携带 tick；渲染插值不能误用未来速度或混合不同水域的坐标。

纹理相位可使用双相位交叉淡化等手段减少无限拉伸，但纹理动画不能替代水动力速度场。漂浮物的位移应由实际流速和受力决定。

## 10. 石头、岸壁与动态障碍

### 10.1 静态几何的分类

- 水面以下的低石头：主要改变床高与有效水深，允许水从上方经过。
- 穿出水面的实体：阻挡其截面内的法向流量。
- 岸壁：不可穿透边界，可叠加摩擦与视觉湿痕。
- 桥墩：局部障碍；桥面不能把整条河错误封死。
- 很细的石缝：网格无法解析时应给出近似与最小尺寸限制。

### 10.2 通量与边界

先在守恒更新中阻止水穿越实体边界，再添加泡沫与尾流细节。静态不可穿透边界的法向相对速度应为零；自由滑移、切向摩擦和粗糙度影响要明确选择。

如果采用部分单元或面开口比例，应防止极小有效单元导致极端时间步限制，并设计正性与预算策略。先做完整单元障碍的可靠版本，再评估亚网格精度。

### 10.3 动态物体双向作用

现有浮力/阻力已经读取水体并对刚体产生力。新增水体反作用时要检查现有 `Game` 调用，避免重复施力。

- 确定物体受流体的水平冲量，以及分配回水体的反向冲量。
- 分配核应归一化，并按水深和有效面积约束。
- 记录限幅、干单元跳过和无法施加的冲量。
- 浮力来自重力与压力作用，不应把全部垂直浮力简单反写成水平速度。
- 完整三维物体—流体系统的动量交换不等于当前二维近似；应明确近似范围。
- 物体移动引起的排水需要体积占据模型，不能直接把水深清零。

### 10.4 尾流与泡沫

尾流来自实际速度变化和边界作用。泡沫可依据压缩、速度剪切、曲率、浅水破碎代理和撞击来源生成，然后平流并衰减。

涡量可以作为诊断或视觉增强信号。人为涡量增强必须说明能量影响，不能用无限增益在静水里持续制造旋涡。

## 11. 落差、瀑布与水量转移

### 11.1 分层方案

优先采用“上游浅水域 + 转移连接 + 下落水片/水滴 + 下游浅水域”。先支持明确配置的落差连接，再考虑自动识别复杂地形瀑布口。

单层高度场无法在同一 XZ 位置表达多层自由水面。自由下落段应有独立表示，不要把垂直水片硬塞进水平水深网格。

### 11.2 建议转移账本，尚未实现

```text
WaterTransferProposal
  transferId, timelineEpoch
  sourceWaterBodyId, destinationWaterBodyId
  sourceRegion, landingRegion
  requestedFlowM3s, actualFlowM3s
  sourceExitVelocityMps
  transitVolumeM3
  pendingArrivals: arrivalTick + volumeM3 + velocity
  deliveredVolumeM3, lostOrExternalVolumeM3
```

若选择考虑飞行时间，水离开上游后进入在途账本，到达后进入下游：

```text
V_total = V_upstream + V_transit + V_downstream
```

初版也可使用明确标注的瞬时转移近似，但必须保持守恒，并且不能再由视觉水滴落地重复加水。

### 11.3 下落运动与落点

- 以出流水速为初值，重力控制下落速度和落点。
- `v² ≈ v0² + 2*g*H` 仅是忽略阻力等影响的尺度估计，不是所有瀑布条件下的精确公式。
- 下游接收水量和适当的冲量/扰动代理；二维浅水无法完整吸收三维入射动量时应说明投影模型。
- 视觉水片截面与流量、水速应有一致关系，避免低流量却出现整面厚水墙。
- 粒子是视觉采样，不是水量计数器；LOD 减少粒子后，水量账本保持不变。
- 水雾由冲击、破碎和局部气流代理驱动，不能在所有瀑布上固定播放同一团雾。

### 11.4 后续三维模拟的触发条件

只有确实需要近景翻卷、多层水片或复杂物体冲击，且已有性能预算时，再评估局部 FLIP/APIC/PBF 或网格三维流体。先明确模拟域、边界交换、表面重建、资源回收、质量误差和退出策略。

## 12. 泡沫、湿润、光学与声音

### 12.1 泡沫

- 区分岸线泡沫、接触泡沫、急流白水、瀑布落点泡沫。
- 给泡沫定义覆盖量、寿命、生成来源和流速。
- 衰减使用时间常数，避免每帧固定乘数导致帧率相关。
- 生成有阈值与平滑过渡，站立静水不应持续全白。
- 尺寸分布与距离过滤要稳定，远景避免高频闪烁。

### 12.2 湿润痕迹

记录接触水位历史或表面湿润度，驱动石头暗化、粗糙度与反射变化。湿润区域应有干燥时间，不应随一帧水位下降立即消失。复用现有材质能力，并核查其是否已支持所需参数。

### 12.3 光学

优先保证水体厚度、IOR、吸收和折射方向正确，再增加焦散与更复杂反射。

- 吸收可用 `T = exp(-sigma_a * L)` 的尺度关系；`L` 必须是明确的水中距离近似。
- 深度缓冲差不总等于沿折射光线的水中路径长度，需要记录近似。
- SSR 失效要有连续回退，不能在屏幕边缘跳黑。
- 水底焦散初版可作为受水深、波面和光源约束的视觉近似，并标注实现等级。
- 法线、位移、折射扭曲和泡沫不能分别使用完全无关的波相位。
- 调整粗糙度不能替代修复错误法线或错误纹理绑定。

### 12.4 声音，可选后续项

脚步、水滴、急流和瀑布声音可消费同一接触事件与流量信号。声音线程不拥有水体权威，音频资源缺失不能中断水体求解。先核查现有音频资源与调度能力，再决定是否加入本阶段。

## 13. 资源、接口、编辑器与兼容

### 13.1 资源演进流程

1. 列出新增字段的用途、单位、默认值、上下界和资源归属。
2. 明确旧资源如何解释；是否必须提升 schema 版本。
3. 同步 JS authoring/cook 与 C++ cooked parser。
4. 更新严格未知字段拒绝规则；不允许只有一端悄悄忽略字段。
5. 同步场景 schema、资源依赖收集、哈希和打包。
6. 编辑器只暴露实际可用的参数和诊断，不显示尚未实现后端。
7. 缺少外部几何或水域连接时给出明确错误，不默默使用另一份资源。

### 13.2 建议按职责组织资源

以下是概念划分，不是现有 JSON 示例：

```text
WaterBody       水域、床高来源、材料、求解预算
WaterSource     局部入口与输入流量
WaterDrain      局部出口与边界条件
WaterObstacle   静态或动态占据表示
WaterTransfer   两水域之间的水量转移与落差
WaterContact    运行时事件，不作为静态资源复制保存
```

优先考虑这些职责能否作为现有 water 资源的受控扩展，避免无必要地创建六套独立资源系统。

### 13.3 编辑器参数建议

展示水深、流速、流向、入口实际流量、出口受限量、障碍掩码、CFL 预算和质量误差。参数旁显示单位。

允许在项目内保存配置、预览和报告；不要把运行时项目的场景保存回引擎 `.screen/`。预览重置要清理事件 epoch、细波纹和在途瀑布水量，或按明确的恢复合同保留。

## 14. 性能、LOD 与资源生命周期

### 14.1 必须测量

- CPU 求解时间及最坏子步数。
- 交互注入耗时与每 tick 活跃事件数。
- 地形/障碍构建耗时，以及运行时局部更新成本。
- GPU 传播、平流、法线、泡沫和绘制各自耗时。
- 上传字节数、常量切片数、描述符与资源数量。
- 活跃水域、粒子、瀑布连接和在途批次数。

当前 256×256 的两个高度纹理、两个速度纹理与一个结果纹理，按 R32 单通道有效载荷约为 1.25 MiB；实际显存还包含资源对齐、上传、描述符和绘制输入。增加速度场与泡沫后需重新统计，不能沿用旧值。

### 14.2 降级顺序

1. 降低远处视觉粒子与水雾数量。
2. 降低远处细波纹、泡沫与光学分辨率。
3. 减少远处高频法线层或反射工作量。
4. 如需降低玩法求解频率，必须另外设计误差、守恒和固定时钟，不得直接随帧率减步。

### 14.3 D3D12 生命周期检查

- CBV 切片满足 256 字节地址对齐，单次 dispatch 参数在执行前不可被覆盖。
- 上传缓冲按在途帧槽隔离，复用前等待正确 fence。
- 同一资源的读写转换、UAV 同步与跨队列等待可解释。
- 场景重置、resize、设备恢复后描述符绑定与旧资源引用一致。
- 创建纹理后先初始化，再采样；不要依赖分配器恰好返回零。
- root signature、HLSL register 与实际 heap offset 一致。
- 多个水域不能意外复用上一水域的深度、常量或事件游标。

## 15. 分阶段实施与完成门槛

### M0：现状审计与可复现基线

交付：当前源码调用图、已实现/已集成/已验证表、运行命令、证据路径与当前限制。

门槛：能解释一次接触从输入到 CPU、GPU、绘制和喷溅的全过程；基线图像确实对应当前构建。文档核查阶段不因历史建议自动运行全量测试。

### M1：多接触事件与真实脚掌交互

优先子项：事件唯一身份、同 tick 多接触、容量截断语义。随后接入脚掌轨迹与垂直入水。

涉及：`body`、`coupling`、`Game`、动画接触适配、`PondDemo`、事件 ABI、专项测试。

门槛：双脚同 tick 不丢事件；同一事件重绘不重复注入；慢走/奔跑/落水平均反应排序正确；瞬移无假尾迹；停止后不继续生成脚步脉冲。

### M2：传播质量、波形尺度与主流平流接口

交付：CPU/GPU 分离诊断、非方形域测试、方向旋转测试、速度快照输入与细波纹平流的最小实现。

门槛：静水无人工漂移；低速均匀流中波包搬运方向正确；与无流基线的能量衰减和偏差有可比较证据；不破坏旧数值守恒。

### M3：局部入口/出口与河床

交付：版本化资源设计、实际流量账本、地形床高和水位差驱动的最小河道。

门槛：入口与出口差额等于域内水量变化；换网格分辨率后指定流量基本一致；静水平衡不过度漂移；干出口不会抽出负水量。

### M4：静态石头与岸壁

交付：低石头床高、出水实体边界、分流与尾流证据。

门槛：无穿透；局部几何变化改变实际流速；静水石头不持续凭空生泡沫；质量误差在本阶段明示容限内。

### M5：动态物体与泡沫搬运

交付：复用已有浮力/阻力、补充经过归一化的反作用，明确位移排水近似；泡沫来源、寿命和搬运。

门槛：不重复施力；同一受控试验中冲量交换可核算；改变视觉泡沫预算不改变刚体运动和水量。

### M6：落差与瀑布连接

交付：明确配置的上下游连接、转移账本、在途或瞬时近似、连续水片、落点扰动。

门槛：上下游与在途总水量守恒；改变视觉粒子数量不改变流量；连接启停与重载不重复交付水量；落差与冲击强度变化有证据。

### M7：光学、湿润与性能收敛

交付：光学分项对照、岸石湿痕、预算报告、LOD 和异常诊断。

门槛：多个视角、帧率与距离下稳定；光学效果能分别开关和检查；降级前后玩法账本保持一致。

M3 与 M4 的先后可按本轮目标调整，但瀑布依赖明确的水量入口/出口合同。不得提前把 M6 的视觉演示当作完整水动力交付。

### 16.1 阈值如何制定

- 先记录现有基线，再为新功能设定容限。
- 给质量误差、流量误差、方向偏差、漂移与运行时长分别定义阈值。
- 接近空水域时使用绝对体积误差，避免用极小分母制造无意义百分比。
- 不同边界、不同格式与不同波形不能机械共用一个阈值。
- 各硬件 GPU 浮点结果未必位级一致；区分同设备重放与跨设备容差。
- 不为过测试而无限放宽阈值；失败后先定位，再更新合理合同。

### 16.2 必须保留的调试视图

水深、床高、权威自由表面、GPU 残差、最终位移、法线、速度与流向、障碍、泡沫来源/覆盖、厚度、折射、反射与置信度。

这些是所需语义，不代表当前所有模式编号已存在。当前水面调试模式范围应从源码读取，新增模式要同步校验、报告和工具，不随意复用旧编号。

### 16.3 截图和报告

- 固定场景、相机、tick、种子和光照，做可比较截图。
- 至少提供俯视、角色近景、石头背水侧和瀑布侧面中的本阶段相关视角。
- 不用单张远景图证明微小波纹或不透水边界正确。
- 报告包含资源哈希、构建来源、配置、时钟、错误计数和证据路径。
- 人工检查原图；自动断言通过后仍应检查尖刺、闪烁、错位和整体不合理的波形。

## 19. 常见错误与禁止的完成声明

- “半径加随机数，真实水体就完成了”：仍需接触语义、传播、流场与边界。
- “GPU 回读正常，所以画面一定正常”：实际绘制可能绑定了另一份纹理。
- “水沿斜坡自己流，因此任何坡床静水都要加速度”：水平自由表面可以处于静水压平衡。
- “入流只是每帧加固定深度”：会受帧率、面积和分辨率影响。
- “石头区域设为干单元就完成所有障碍”：会误挡水下石头，并可能丢失水量。
- “画了尾流贴图就实现绕流”：应检查实际通量和速度。
- “已有浮力函数等于完整双向耦合”：要核查游戏调用、反作用与占据体积。
- “每个喷溅粒子落地加一份水”：视觉 LOD 会改变水量并容易重复记账。
- “保持旧水位再升高河床不会影响水量”：可用空间减少时必须处理排水。
- “限幅后没有 NaN，因此数值稳定”：还需检查能量、时间债务、守恒和限幅频率。
- “历史报告通过，所以本轮可以免验”：构建、资源和测试版本可能已改变。
- “把所有阶段都写了类和 UI 就算交付”：需要可运行路径和对应阶段证据。

## 20. 一手资料与应用边界

[GPU Gems 3，Chapter 30：Real-Time Simulation and Rendering of 3D Fluids](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-30-real-time-simulation-and-rendering-3d-fluids)

### 20.3 使用资料的要求
