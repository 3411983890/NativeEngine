# 纹理与材质资产管线方案

- 版本：草案 v0.1
- 日期：2026-10-21
- 状态：方案设计，尚未实施；本文件中的格式、接口、指标均为提议。
- 实现：v0.3 已落地 [MATERIAL-PIPELINE.md](MATERIAL-PIPELINE.md)：PNG → mip → `.ngtex`（RGBA8/BC1/BC3/BC5/BC7）→ 预算求解 → bindless 独立纹理 → 材质表（wetness/wear、自发光）→ 小镇；TX3 的增量缓存/热重载与 TX5 的发布门禁仍按计划推进。
- 基线：NativeGPU 0.10.0；已有原生 D3D12、Web/Electron 编辑器、场景事务、内容寻址构建、预算管理器、骨骼蒙皮与回放证据。
- 方向：让每份材质带着可组合的配方、可解释的开销和可重放的证据进入引擎。

## 1. 希望做出的体验

在编辑器输入：

> 把小院改成雨后的旧工业区。铜门有氧化和擦痕，砖墙略潮湿，人物衣服保留原来的颜色。这个场景的纹理预算是 96 MiB。

系统给出一份可检查的修改：哪些物体会变、共享哪些纹理、湿润与磨损参数如何变化、编译后预计占多少显存、哪些远景资源需要降低分辨率。确认修改后，原生预览呈现结果；撤销恢复此前的材质引用与参数。

96 MiB 是这条演示需求的可配置预算，不是当前引擎已经达到的实测结果。自然语言入口放在结构化配方与事务稳定以后接入。

第一轮可见成果是一组能直接放进小院的砖、木材、布料、裸金属与涂漆金属，同一份基础材质能派生多个实例，并展示干燥/潮湿、完好/磨损两个变化维度。

## 2. 四个值得做的创意

### 2.1 用“表面经历”组织材质

以一扇涂漆铜门为例：

```text
铜基底 → 漆层 → 指定区域磨损 → 暴露铜面氧化 → 表面受潮
```

用户操作“磨损程度、氧化程度、湿润程度”，配方同时调整颜色、粗糙度、金属度及相应遮罩，保持通道之间的联系。例如，去掉漆层会暴露基底；氧化会同时改变它覆盖区域的颜色与反射参数。

- 首版只交付 wetness / wear 两个可验收控制，氧化作为后续配方。
- 遮罩先接受作者提供的图片与确定性程序生成结果；曲率/遮挡等几何烘焙以后再接 Blender Worker。
- 主要处理离线烘焙；运行时只保留少量标量和遮罩组合。动态受潮是外观近似，不承诺流体、积水或真实化学过程。
- 材质实例共享贴图，实例差异使用少量参数与稳定 seed。seed 从实体 UUID 与配方版本导出，不能每帧随机改变。
- 木纹等有方向的材质声明方向约束；随机变体不得任意旋转它。

**验收演示：** 十二件道具共用少量基础贴图，呈现可复现的个体差异；调节全局湿度时，作者指定的受潮区域发生连贯变化。

### 2.2 给编译器一个“质量与开销”面板

导入时产生几个候选版本，例如 512、1K、2K。每个候选都有实际解码后的质量误差、纹理净负载、构建耗时和依赖清单。

用户可以指定：

- 门与人物属于重点对象，优先保留细节。
- 远景墙面可以先降分辨率。
- 全场景纹理必须落在预算内。

编译器先对共享纹理去重，再挑选满足质量下限的候选版本；无法同时满足质量和预算时，明确列出冲突与可选调整。初版采用确定顺序的贪心策略，并记录每一步，不宣称全局最优。

一个尺度参考：2K 的 BaseColor、Normal、ORM 三张贴图，若分别采用 8 bit/texel 的 BC7、BC5、BC7，完整 mip 链的纹理净负载约 **16 MiB**；十份互不共享的同规格材质约 160 MiB。这不含 GPU 分配对齐、上传缓冲与旧版本并存的开销。[BC 格式说明](https://learn.microsoft.com/en-us/windows/win32/direct3d11/texture-block-compression-in-direct3d-11)

运行时预算接入作为后续扩展：真正降低显存需要换成缺少高分辨率 mip 的较小资源，并在旧资源的 fence 完成后释放；单纯提高采样 mip bias 不算节省显存。复用 R08 时沿用其已实现的单向降档规则，不提前承诺自动升档。

### 2.3 做一个能解释问题的材质体检台

同一材质在固定光照下展示：正方体、球体、UV 镜像测试片、带 UV 接缝的测试网格和当前蒙皮角色。预览使用真实原生截图，沿用现有编辑器快照通道。

可切换观察：

- 最终着色、基础色、世界法线、粗糙度、金属度、AO。
- 原图、解码后的压缩图与误差图。
- mip 级别与远距离闪烁。
- UV 密度、切线方向、镜像接缝。

点一个问题像素，能看到它来自哪张源图、哪个通道、哪个构建步骤和哪个参数。优先诊断常见错误：颜色被重复转为 sRGB、法线方向不一致、金属度误接粗糙度、UV 缺失、采样器不兼容。

**验收演示：** 故意放入一张按颜色空间导入的法线图，诊断能定位错误的语义声明；修正后给出前后图和构建差异。

### 2.4 每次修改附带一份“资产收据”

收据记录输入内容 hash、处理器与版本、操作参数、seed、依赖、产物 hash、显存净负载、构建耗时和验证结果。来源、作者以及可选的生成任务信息作为附属元数据保存。

例如修改 roughness：修改预览说明它会重建哪个 ORM 产物、影响哪些材质实例、哪些内容继续命中缓存。失败时保留当前可用版本，错误指向资产和步骤。

自然语言和 MCP 入口最终提交同一种结构化 AssetPatch / ScenePatch，编辑器和 AI 复用预览、提交与撤销，不建立另外一套直接改文件的入口。

## 3. 当前代码决定了哪些基础必须补

| 当前事实 | 对本方案的影响 |
| --- | --- |
| `assets/scene.schema.json` 中材质是内联 albedo / roughness / metalness / pattern | 需要资产引用与实例参数；旧场景需要显式兼容 |
| `renderer/d3d12_renderer.cpp` 内置 64×64、单层 mip 的纹理数组 | 需要真实图片导入、完整 mip、GPU 压缩和独立纹理资源 |
| `host/scene_loader.cpp` 读取 albedo，但 `Game::renderPoses()` 没有把它送入着色参数 | 必须验证从场景字段到实际像素的整条数据链 |
| `materialHandle` v2 的低 16 位被定义为纹理 SRV 槽位 | 多贴图材质需要独立的材质记录，不能悄悄改句柄含义 |
| 静态 glTF 管线只保留 position / normal；蒙皮管线有 UV，没有 tangent | 法线贴图还需要 UV、切线、接缝与蒙皮切线处理 |
| VS / Mesh Shader 的材质采样与光照逻辑分散 | 需要共用材质求值函数，避免新能力只在一条路径上生效 |
| 当前光照是近似模型 | 接入 PBR 贴图不等于已经完成全套 PBR 光照与 IBL |
| 已有内容寻址构建、事务、预算和报告 | 复用这些基础，扩展到纹理与材质的依赖闭包 |

还有一个实际限制：当前光栅 root signature 的开销为 56 个根常量 + 两个根 CBV 各 2 + 一个描述符表 1，共 **61 DWORD**。D3D12 上限为 64；扩展前应把大块 draw 常量移入逐帧缓冲，根参数只携带索引和少量绑定。[Microsoft 的限制与计费规则](https://learn.microsoft.com/en-us/windows/win32/direct3d12/root-signature-limits)

## 4. 总体架构

```text
作者图片 / glTF 材质 / 程序化配方
                  ↓
         导入声明与语义校验
                  ↓
      纹理处理 DAG + 材质配方编译
       ├─ 色彩与通道规范化
       ├─ mip / 压缩 / 质量候选
       └─ 依赖 hash / 收据 / 缓存
                  ↓
      不可变 TextureCook / MaterialCook
                  ↓
      版本化资产目录 + 场景依赖锁定
                  ↓
      加载 / 上传 / 帧边界发布 / 延迟回收
                  ↓
   VS / Mesh Shader / Skin VS 共用材质求值
```

编辑器草稿与构建产物分开。源文件仍可由作者编辑，导入为已确认的内容快照后再构建；运行包只依赖锁定的编译产物。

### 4.1 四类数据身份

| 身份 | 用途 | 是否写入持久资产 |
| --- | --- | --- |
| Asset UUID | 作者看到的长期资产身份，改名和移动时保留 | 是 |
| Artifact hash | 某一组输入与构建规则得到的不可变产物 | 是 |
| MaterialHandle | 当前运行会话里的材质记录句柄 | 否 |
| TextureHandle | 当前会话里的纹理资源/描述符句柄 | 否 |

UUID 在首次作者导入时分配并保存；重建缓存不得重新生成 UUID。资产目录把 UUID 与 revision 解析到 artifact hash；发布时写入依赖锁，保证离线重放使用同一份内容。

### 4.2 v3 迁移提议

`docs/GEOMETRY-LAYOUT.md` v2 已冻结。下列变化需要新版本与迁移工具，本方案不把它们当成已生效的格式：

- 材质句柄低位在新契约中索引 MaterialRecord；TextureHandle 单独指向纹理资源。两者可保留 16+16 的编码形状，但必须使用不同类型与接口。
- 离线几何记录使用包内 materialRef，指向材质依赖表。加载时才解析运行句柄；不把 GPU 槽号或代际写成可跨会话的资产身份。
- 旧 v2 包继续走 legacy 解释。已知内置材质可显式映射；任意旧非零句柄缺少对应资产信息时要求迁移映射，不能凭槽号猜材质。
- 新场景 schema 提供 materialRef 与有类型的实例 overrides；与旧内联 material 字段互斥，读旧写新通过显式升级事务完成。
- 纹理与材质各有独立格式版本。需要增加 UV/tangent 或修改蒙皮顶点布局时，分别升级几何包与动画资产容器；不覆盖旧产物目录。

基础管线先使用普通的有界描述符表，每次 draw 绑定需要的贴图。现有八槽 legacy 路径继续兼容；新资产库的数量不等于八个。B3b 材质主路径 heap 索引仍遵循既定的 B2 → B4 → B5 → B3b 顺序，不通过资产管线提前宣称完成。

## 5. 纹理与材质的首版规范

### 5.1 源图、运行格式与语义

首版先支持 PNG；JPEG 作为基础色输入随后接入。TGA、HDR、KTX2 与更多导入器按独立工作包扩展。Windows / D3D12 运行产物先使用 DDS；PNG 留在作者源文件层。

| 用途 | 内部语义 | 建议运行格式 | 缺省值 |
| --- | --- | --- | --- |
| BaseColor | RGB 使用 sRGB 存储、采样转线性；factor 为线性 | BC7 sRGB；无损参考为 RGBA8 sRGB | 白色 |
| Normal | 线性向量数据，约定切线空间方向 | BC5 UNORM；受质量门禁约束 | 平法线 |
| ORM | R=AO、G=roughness、B=metalness，线性数据 | BC7 UNORM；可按质量合同选择其他格式 | AO=1、roughness=1、metalness=0 |
| Emissive | sRGB 颜色 + 线性强度 | 可选 BC7 sRGB | 黑色 |
| 表面遮罩 | 线性数据，按名字声明每个通道 | 按实际用途选择，进入采样与预算统计 | 配方明确指定 |

颜色与数据贴图的区分、roughness/metalness 通道沿用 glTF 的语义；法线图的作者约定必须显式声明并在导入时统一。[glTF 材质规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#materials)

ORM 只有在 UV 集、UV 变换、采样规则和目标分辨率兼容时才合并。否则保留独立输入，或要求显式烘焙，不能为了减少文件数改变采样语义。

### 5.2 mip 与确定性构建

- 颜色 mip 在线性空间滤波；法线按向量处理并归一化；标量按各自语义处理。进阶法线方差/粗糙度补偿另设版本与验收。
- 固定解码、滤波与编码器版本和参数。优先使用 DirectXTex，压缩参考路径关闭 GPU 编码；仍须两次清缓存重建逐字节比较，软件编码本身不等于已证明确定性。[DirectXTex Texconv](https://github.com/microsoft/DirectXTex/wiki/Texconv)
- buildKey 包含规范化像素 hash、语义、色彩空间、mip 规则、压缩设置、目标 profile、处理器版本与烘焙 seed；不包含时间戳和绝对路径。
- 共享去重以实际处理语义和产物为准。名字相同不代表同一纹理；相同像素被当作颜色与数据处理时也不能错误合并。
- 收据里的构建时间、机器信息与来源说明不混入决定产物字节的规范化 manifest。

### 5.3 法线与几何桥接

静态与蒙皮导入都需要保留 TEXCOORD_0 和 TANGENT，缺切线时采用固定版本的 MikkTSpace。UV 镜像、切线 handedness 与蒙皮后的方向必须进入测试。[MikkTSpace](https://github.com/mmikk/MikkTSpace)

当前静态几何去重只使用位置/法线；新增 UV/tangent 后，去重键和 cluster 顶点打包也要升级。切线重建造成拆点时，同步复制关节与权重，保留动画片段数据。

首版明确只接受已支持的 UV/采样子集。缺 UV、退化 UV 或不支持的 glTF 材质扩展要给出带资产定位的诊断。

### 5.4 共用材质求值

建立共用 MaterialSample → SurfaceAttributes → Lighting 三层接口。三条几何路径复用采样语义和着色函数；有界表与未来 heap 索引只替换资源获取部分。

新材质使用明确的基础色乘法与线性空间计算。旧内置图案通过 legacy 模板保留解释，避免把修正旧 albedo 链路变成无记录的全场景外观变化。

第一版交付不透明材质、共享的金属度—粗糙度直射光着色（GGX）和已有环境近似；IBL、玻璃、皮肤 SSS、水、毛发、任意节点图、UDIM 与虚拟纹理另外排期。多张贴图接入与这些效果的实现分别验收。

## 6. 生命周期、事务与回放

### 6.1 发布一份完整快照

构建先写临时目录、校验、再发布不可变对象。跨多个材质与场景引用的修改，通过资产事务发布一个带 expectedRevision 的目录快照；中间产物在提交前不可见。撤销切换引用和参数，旧对象暂留供引用与回滚使用。

这是对现有 ScenePatch 的扩展工作，不能直接宣称当前场景事务已经支持任意图片文件的原子提交。

### 6.2 GPU 发布与回收

资源经历 Pending → Uploaded → Ready → Retiring → Released。Ready 以前继续使用旧版本；材质记录与描述符按帧快照发布，旧版本等待所有相关队列的最后使用 fence 完成后回收。不得覆盖在途帧仍在使用的绑定。[D3D12 描述符表版本管理](https://learn.microsoft.com/en-us/windows/win32/direct3d12/descriptor-tables-overview)

纹理热重载通过独立资源路径完成，不调用 Game::initialize()，因此资产预览更新可以保留角色当前的位置和动画。首个加载版本可同步完成，异步上传与在途替换在 TX3 验收后启用。

### 6.3 确定性的边界

- Gameplay / 动画摘要不写入物理描述符槽号、异步加载顺序、显存地址或预算降档的瞬时状态。
- 录制锁定内容快照；视觉重载事件可记录 tick 与新 artifact hash，支持还原当时看到的版本。
- 当前 Game::digest() 包含部分渲染派生字段，动画资产指纹也覆盖网格；需要显式升级摘要契约，区分 motionContentHash、skinContentHash 与 materialArtifactHash。旧记录按旧版本解释，不能默默改含义。
- 质量候选与性能状态单独记录。固定 profile 和内容快照下做图像对拍，不要求不同质量档的最终画面逐像素相同。

## 7. 分批实施与验收

| 工作包 | 范围 | 前置 | 具体交付 |
| --- | --- | --- | --- |
| TX0 契约与迁移样板 | 资产身份、依赖锁、场景引用、材质/纹理句柄、root 参数预算、摘要边界 | 现有 0.10.0 | 草案转为版本化 schema；旧包迁移与拒绝用例 |
| TX1 首条纹理链路 | PNG → 语义校验 → mip → DDS → 原生采样 → 运行包 | TX0 | 把自己的图片贴进小院；新材质基础色参数确实影响像素，旧 albedo 规则通过显式迁移处理；有界表路径可用 |
| TX2 多贴图与材质一致性 | Normal/ORM、UV/tangent、实例参数、共用求值与 GGX 直射光、体检视图 | TX1 | 静态、Mesh、蒙皮三条路径均可消费新材质；镜像 UV 样板正确 |
| TX3 资源生命周期 | 增量缓存、事务快照、热重载、帧快照、延迟回收 | TX2 | 更换一张图片只重建依赖闭包；在途更新和故障恢复可重放 |
| TX4 表面配方 | wetness/wear、稳定实例差异、预算候选、编辑器与结构化 AssetPatch | TX3 | 十二件道具共享基础贴图；参数变化可预览、撤销、解释和计价 |
| TX5 发布门禁 | 质量合同、预算、打包闭包与完整回归 | TX1 起逐步补齐，最终依赖 TX4 | 版本化证据，失败使 CI 变红；新能力分别报告 implemented |

首个开发批次建议选择 **TX0 + TX1**，同时放入体检台与表面控制的最小界面骨架；随后 TX2 补齐法线和 ORM。首版收口于 TX4/TX5 的完整链路，先把湿润与磨损做出可信效果。

自然语言材质编辑在结构化 AssetPatch 稳定后接入。模型生成的新贴图必须进入同一套导入、构建和验证过程；运行时材质求值不依赖模型服务。

## 8. 门禁与报告

**硬性门禁：**

- 同一冻结构建环境下，两次清缓存重建的产物与 manifest 字节一致。
- 依赖闭包完整，运行包从独立目录启动，无源图或构建工具仍能显示材质。
- 修改一张源图只重建它及真正依赖它的打包贴图/材质；无关纹理与动作 Clip 的内容 hash 不变。
- 缺图、损坏 DDS、错误颜色语义、过期句柄、越界 mip、缺 UV/tangent 有稳定 NG-E-ASSET/TEX/MAT 类诊断；失败保留旧可用版本。
- 在真实在途帧上反复替换并验证延迟回收，设备重建后恢复；对象计数无持续增长。
- 快照发布、引用撤销、热重载与严格回放保持约定语义；现有回归继续全绿。

**质量候选目标，需基准集实测后冻结：**

| 项 | 候选门限/方法 |
| --- | --- |
| 基础色压缩 | SSIM ≥ 0.99，并记录线性颜色误差 |
| 法线压缩 | 归一化解码向量角误差 P95 ≤ 2°，同时报告最大值 |
| roughness | 绝对误差均值 ≤ 0.01；高光变化使用固定光照截图复核 |
| 路径一致性 | 相同表面输入的量化 SurfaceAttributes 一致；最终图像容差由基准确定 |
| mip 正确性 | 线性颜色、常量向量、标量梯度的解析样板 + 远距离截图 |
| 预算 | 共享去重后的纹理净负载和实际 GPU 分配分别统计；上传/重载峰值另列 |

这些数值是提议，尚无本项目实测结论。无法达标时提高质量档、使用无损版本或报告预算冲突，不以自动放宽门限换取通过。

每次构建输出收据；每次运行报告包含资源数、引用数、缓存命中、mip/格式/profile、实际上传字节、上传次数、GPU 驻留与重载峰值、延迟回收积压及失败资产 ID。能力查询、加载成功、实际采样与效果实现分字段。

报告继续使用 `reports/<version>/<commit>/<timestamp>/`。计划中的独立入口为 `tools/assets.ps1`，逐步接入 verify；新场景图像基线必须查看差异后显式接受，不能在普通 CI 中自动更新已有基线。
