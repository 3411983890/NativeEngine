# Web 编辑器与原生引擎

当前采用 **Web 编辑器 + 原生 D3D12 引擎**：Electron 提供桌面界面，Node.js 服务复用现有场景事务，`NativeGPU.exe` 在独立窗口中运行游戏。浏览器版本使用相同界面与服务，便于本地开发和检查。

本路线替代“先修改并构建 Chromium，再开始编辑器 UI”的顺序。当前不编译浏览器源码，不新增 Chromium 补丁或自定义 Mojo 接口；旧方案保留在 [CHROMIUM-START.md](CHROMIUM-START.md) 作为以后确有需求时的参考。引擎版本仍为 0.10.0。

## 启动

要求：Windows 11 x64、Node.js 22+、PowerShell。原生窗口与快照还需要支持 D3D12 的显卡，以及项目的原生可执行文件。

在项目目录执行：

```powershell
npm install
npm run editor
```

首次安装会下载锁定版本的 Electron。若 `build/NativeGPU.exe` 不存在，先构建原生程序：

```powershell
npm run build:native
```

只调试 Web 界面时：

```powershell
npm run editor:web
```

打开终端输出的本机地址。浏览器和 Electron 连接的是同一套本地场景操作，不需要模型凭证或外部服务。原有 `npm run start` 继续直接打开原生程序。

## 编辑流程

1. 从场景列表打开 `assets/` 内的 `.scene.json`，通过实体列表或二维顶视布局选择实体。
2. 在属性面板修改名称、位置、缩放、颜色或碰撞开关。修改先进入本地草稿，布局随草稿更新，场景文件尚未改变。
3. 点击“预览修改”，由现有事务层校验整批命令并返回实际差异。无效数值、场景约束或版本冲突会显示错误，不会写入半个场景。
4. 检查差异后提交。服务以项目 ID 与 `expectedRevision` 原子提交一次，revision 增加一次，撤销记录由现有场景模块维护。
5. 启动原生预览窗口查看实际 D3D12 画面。提交后原生程序自动热重载；“撤销”通过同一服务提交反向恢复，revision 继续增加。

也可以新增方盒道具或删除实体。删除玩家、删除最后一个地面等违反场景约束的操作仍会被事务校验拒绝。未提交草稿不会写入文件；离开编辑器前应提交或丢弃草稿。

其他工具或 Agent 修改同一场景时，旧 `expectedRevision` 会被拒绝。界面保留本地草稿供检查；重新加载新 revision 后需要重新预览，而不是静默覆盖外部修改。

## 画面与原生进程

- **场景布局**是二维顶视图，用于选择和检查实体的位置、尺度与颜色，不是 D3D12 渲染，也不代表遮挡、材质或灯光的最终效果。
- **原生预览**是独立的 `NativeGPU.exe` 交互窗口。编辑器可以启动、停止自己创建的预览进程并显示其状态，不会停止其他终端启动的原生程序。
- **原生快照**按需运行一次隐藏的原生截图任务，显示真实渲染的静态 PNG。它不是实时视频，也不是跨进程共享纹理通道；未提交草稿不会出现在快照中。
- 原生程序仍约每 400 ms 检查已提交场景，热重载会重新初始化玩法状态。当前没有运行中状态迁移，也没有逐帧把草稿发送到引擎。
- 缺少原生程序时，场景编辑仍可使用；启动预览或截图会显示明确错误。

## 模块边界

```text
Web 界面（本地草稿、选择、差异展示）
    ↓ 受控场景/运行操作
编辑器服务
    ├─ 现有 Node 场景事务（查询、预览、提交、撤销）
    └─ 原生进程管理（启动、停止、按需快照）
          ↓ 读取已提交场景
      NativeGPU.exe（模拟、D3D12 渲染、热重载）
```

编辑器与 MCP 复用同一事务实现，不另建直接写 `assets/` 的路径。Web 界面不持有任意文件访问或任意命令执行能力；浏览器服务只用于本机开发，不应暴露到外网。

本次增加了命名材质的 `wetness` / `wear` / `roughness` / `metalness` / `uvScale` 参数面板（通过 `material_patch` 原子写入），仍没有模型调用、自然语言任务编排、资产导入、灯光属性编辑、三维操纵柄或内嵌实时视口。

## 验证与后续工作

```powershell
npm test
npm run test:editor
```

`npm test` 运行既有 Node 测试及编辑器新增测试；`npm run test:editor` 只运行编辑器服务和传输相关测试。原生渲染验证仍通过既有 `npm run verify` 入口进行。桌面窗口、浏览器界面和实际 D3D12 快照需要在有相应运行环境的机器上检查，单元测试不能替代 GPU 证据。

后续先单独验证成熟容器的共享纹理导入能力，再决定是否内嵌原生视口。需要测量复制次数、同步等待、输入延迟、缩放、最小化和设备恢复行为；[OUTPUT-CONTRACT.md](OUTPUT-CONTRACT.md) 保留这些未来 GPU 输出要求。当前编辑器交付不代表该契约已实现，也不代表 G2 共享纹理关口通过。
